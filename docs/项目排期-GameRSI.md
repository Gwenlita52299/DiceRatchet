## 5. 关键路径与提速选项

**关键路径**：GAME → MOD-01 → MOD-02 →（MOD-03）→ MOD-04 → MOD-06 → MOD-07 → M3。单人开发时所有任务都在关键路径上，下面几项是能压缩工期的地方：

| 选项 | 节省 | 代价 / 前提 |
|---|---|---|
| 加 1 名协作者，并行做 MOD-03（与 MOD-01/02 同步）和 MOD-08（与 MOD-04/05 同步），即 Spec §6 标注的并行机会 | 约 35 个工作日，M3 可提前到 2027-03 上旬 | 需要按 Spec §4.7 签名表先定好接口桩；两人都要熟悉 INV-1～7 |
| MOD-02 的审计规则集和蜜罐只做 M0 必需部分（v1.0 规则），v1.1 规则推到 M1 以后 | 约 3 个工作日 | M0 期间泄漏覆盖面变小；G4 蜜罐自测必须保留 |
| M2 冒烟改用 K=10、H=20 的小配置 | 约 0.5 天实跑 | 冒烟不作为结论，只验证闭环能跑通 |
| 实跑放在夜间或周末 | 实跑的 5 天大部分可以不占工作日 | 需要 `--resume` 稳定（MOD-06 T-06-7/8），并做好断电保护。**2026-10-04 追加**：长跑必须先 `caffeinate -i`，否则 macOS 空闲休眠会把进程静默挂起（实测 8 h 墙钟只推进 ~30 min 计算量，见 M1 验收报告 F19） |
| **新增（2026-10-05 重标定：这条现在是第一优先级）** 按 §6 首要风险的结论下调 `C`（候选数 2→1）与 `S`（冒烟 5→2） | 按**实测**口径：M3 从 ≈540 h 压到 ≈390 h（`E_gen` 165→120 局/代），约省 6 天连续推理 | 候选数少一半会削弱「多候选择优」的演化信号；需在 M2 冒烟里先确认 C=1 仍能产出 ≥1 轮可判定的演化 |
| **新增（2026-10-05 重标定：这条的优先级同样上调）** 实现 prompt/KV 前缀复用（`inference.cache_prompt` 目前只是配置项，MLX 后端未真正复用 prefill） | 预填占单次调用 ~40–50%（实测 prompt 2500–3000 token，`t_d` p50 7.9 s），若命中率 80% 可省约 1/3–1/2 时间；这是唯一能直接砍 `t_d` 的杠杆 | 需要 MOD-03 补 KV cache 复用，属新工作量（~1 人日）；且要保证 `eval` 模式的确定性不受影响 |
| ~~**新增** M2/M3 长跑前先补 `--resume` 与逐局落盘（见 M1 验收报告 F18）~~ ✅ **已于 2026-10-05 实现** | 不直接省时间，但避免 114 h 的 M3 因一次中断全部重跑 | `run_eval(on_result=…)` 逐局增量落盘 + `baseline --resume`（按 `episodes/<split>/` 跳过已完成 seed，不要求 `state.json`）；与 MOD-06 T-06-7/8 的断点语义各自独立（编排续跑仍看 `state.json`） |

## 6. 排期风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **已发生（2026-10-04 实测；F22 已于 2026-10-05 修复）** 实测单次决策耗时 `t_d` 高于 Spec §8.6 的估计值 | M2/M3 实跑时间成倍增加 | **实测 `t_d` p50 = 5.687 s（原估 3 s，×1.90）**；`E_gen` 14 h → **25 h/代**，M3 全程 60 h → **114 h（4.7 天）**。已回写 Spec §8.6；**建议 M2 开工前先下调 C（2→1）与 S（5→2）**，把 M3 实跑压回约 2.5 天——该决策占用 M2 的 `E_gen` 硬约束（`loop.max_episodes_per_generation`），必须在 MOD-06 联调前定。**F22 已修（2026-10-05）**：三基线此前走「每 env 步问一次模型」（实测 3.1 次推理/决策点），现已改走 MOD-04 `PolicyAgent(mode="baseline_fixed_prompt")`，**每个决策点一次推理**。**但 F22 修复后实测发现真实成本反而更高**：`D` 不是 96 而是 **185**（LLM 的 `steps/D`=1.78 vs 启发式 3.0）、每决策点 1.6–1.8 次调用、`t_d` p50 **7.9 s**（实际 prompt 2500–3000 token）→ **单局 43 min、`E_gen`≈118 h、M3 全程 ≈540 h（22 天）**，`fixed_prompt` 单独 n=40 就要 **29–34 h**（见 [M1 验收报告 §14.18](reviews/2026-10-04-M1验收报告.md)）。**排期必须按这个口径重排** |
| MOD-02 工作量最大（18 人日），且安全相关代码返工概率高 | M0 延期 | 先交付投影和门面，让 MOD-03/04 可以提前联调；guard 与审计随后补齐 |
| **已触发（n=10 归档后）** 8B 模型在 hard × 6 关下近乎零通关 | 演化增益测不出来 | M1 基线出来后，如果 fixed_prompt 通关率 < 5%，改用 medium × 6 关（GAME D-34 已支持），并在 Spec §8.6 登记。**实测（H1 子集 seed 2000–2009，n=10，三基线同源，run `m1-real-h1n10b`）：`random` 0/10 = 0.0%（CI [0.000, 0.278]）、`heuristic` 4/10 = 40.0%（CI [0.168, 0.687]）、`fixed_prompt` **0/10 = 0.0%（CI [0.000, 0.278]）**、10 局全为掉光心死亡（`degraded_n=0 / n_dropped=0`）。**结论修正：`fixed_prompt` 通关率 0.0% < 5%，Spec §8.6 的阈值条件已触发**——hard × 6 关对 8B 基线偏难，M3 的主口径应按该条款改用 medium × 6 关（或在 hard × 6 上承认基线为 0 并据此重设判据）。旧 run `m1-real-h1n10` 的 1/9 = 11.1% 不再作为口径（两次都非重跑，见 [M1 验收报告 §14.6](reviews/2026-10-04-M1验收报告.md)）。⚠️ 两次 n=10 的 CI 都很宽（上限 27.8%），且 `D` 跨局差 7.4 倍——M3 若要把 4–5pp 量级的增益坐实，必须按 §6 首行把 heldout 的 n 或重复次数提上去 |
| 春节前后 MOD-06 跨假期 | 上下文切换 | 春节前完成 MOD-06 的单测部分，节后直接进入联调 |
| M3 test 集只能解锁一次 | 失误后无法重来 | M3 验收前先在 H2 篮子上完整彩排一遍 |
| **新增（2026-10-04）** M1 的真实模型缺陷只能靠「权重落盘 + 一次真实冒烟」暴露 | 三个模块的「已交付」是假象（MLX 后端在真实 `mlx-lm` 上完全跑不起来，见 M1 验收报告 F14–F16） | 把「权重落盘 + `inference probe` 退出码 0」写成 **M2/M3 的准入条件**，并在每个里程碑的 CI 里跑一次真实小样本（如 5 条 prompt）而非全假模块 |
| **新增（2026-10-05，已修）** `plan` 契约不完备让单决策点调用数翻倍（F23） | 若照旧计算，`E_gen`/M3 全程被高估约 **2.3×**（25 h→57 h、114 h→260 h），排期会白留一倍时间 | 两条模板对称补「`play_face` 的 dieId+slotId 是配对、同一 plan 内不得重复使用 slotId/dieId、`use_ability` 需 `usesLeft>0`」，并写明「任一动作失效会让整个决策作废重试」。实测 before：2.29 调用/决策点、25% 决策点退化；受控对照 after（照抄配对的假客户端）：1.07 调用/决策点、1.2% 非法。n=40 真实跑批的 after 数字见 [M1 验收报告 §14.15](reviews/2026-10-04-M1验收报告.md) |
| **新增（2026-10-05，已修）** `evals.seed_timeout_s` 是**墙钟**预算，与并发度耦合（F24） | 1800 s 会把 n_workers 共享模型的局全部判成 `E_EVAL_TIMEOUT`/dropped（实测把 n=40 整批作废，且报告只显示 `n_dropped=40`，不提示「超时太紧」） | 已调到 **5400 s** 并写下推导（`300 × 1.5 × 12 s(p95) × 2 worker ≈ 10800 s` 取 1/2 余量）；**M2 建议改成计算量预算**（`max_llm_calls` 或等效推理秒数），别让预算随 `n_workers` 漂移 |

## 7. 跟踪方式

- 每完成一个任务，在对应模块 PRD 的 §15 中标注实际人日；每周把实际进度与本表对比一次。某里程碑累计偏差超过 20% 时，重排后续里程碑并在 §8 记录。
- 里程碑验收以 Spec §7 与 §9 质量门为准，验收结论写入 `docs/reviews/`。
