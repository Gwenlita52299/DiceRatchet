## 1. 本轮结论（一句话）

`policy` / `reflection` / `proposer` 三个模型角色现在**只由配置决定**：A0/A1/B0/B1/C0/C1 六个臂
可以仅改 `configs/default.yaml`（或 `DICERATCHET_EXPERIMENT__ARM=` / `DICERATCHET_MODELS__*=`
环境变量）切换，业务代码（MOD-04/06/07/08）零改动、且不出现 MLX / llama.cpp / DeepSeek SDK /
HTTP 客户端的直接耦合。切换方式见 README「模型角色与实验臂」小节。缺模型、缺 provider 配置一律 fail-closed，不静默降级。

## 2. 设计决策与理由

### 2.1 DeepSeek 走 `backend: deepseek`，复用 `BackendManager`（而不是另起一套 adapter 栈）

Issue 的架构图写的是 `DeepSeekAPIAdapter`，但现有 MOD-03 已经有完整的「三级 JSON 策略 + schema
校验 + 修复重试 + 上下文守卫 + 内存预算 + 埋点」。如果 API 走平行的一套，就会出现两套语义
（谁负责 schema 修复重试？429 谁重试？usage 谁记？），而 Issue 的验收标准恰恰要求
「429/5xx 错误映射**与本地后端一致**」。

因此：适配器类名按 Issue 要求叫 `DeepSeekAPIAdapter`，但它实现的是 MOD-03 **唯一的 `Backend`
契约**（`load/unload/generate/generate_json/health` + `name/model_id`），注册为
`backend: deepseek`。于是「API 后端」与「本地后端」在 `BackendManager` 眼里完全同形 ——
`execute_json_call()` 在两者上跑同一条修复重试路径（有测试直接验证这一点）。

### 2.2 臂放在 `configs/default.yaml` 的 `experiment.arms`，不另开 `configs/arms.yaml`

- 臂定义因此天然进入 `config_hash` → **换臂即换 run-id 族**（F10），六个臂的产物不会互相污染；
- 环境变量覆盖（`DICERATCHET_EXPERIMENT__ARM=B1`，B-30 的 `__` 分层）无需为新文件再写一套加载器
  （当前 CLI 只有 8 个显式覆盖键，没有通用 `--set`，因此配置层与环境变量就是切臂的两条路）；
- 代码默认值（`ExperimentConfig.arms` 的 `default_factory`）与 YAML 一致，并有单测钉住防漂移。

### 2.3 优先级与「`--model` 不破」

```
experiment.roles.<role>  >  experiment.arms[arm].<role>  >  models.<role>  >  inference.model_id
```

空字符串 = 继承下一层。这条继承规则是刻意保留的：`--model` 写的是 `inference.model_id`，
所以

- A 臂 + `--model mock` → 三角色全是 mock（**离线冒烟的既有语义不变**，这是最容易踩的回归点）；
- B 臂只钉住 `proposer: deepseek-flash`，`--model qwen3-8b-q4` 仍然决定决策/反思模型；
- 配置里显式写 `models.proposer` 或 `experiment.roles.proposer` 才是「明确绑定意图」，优先于 `--model`。

臂是**差分**而非全量声明，正是为了让「继承」在六个臂之间保持可用。

### 2.4 契约下沉（`inference/client.py`）

`InferenceClient` / `BackendInferenceClient` / `coerce_client` 原在 `agent/policy.py`。角色提供者
在 MOD-03，若契约留在 MOD-04，MOD-03 就得反向 import MOD-04（分层倒挂）。因此契约与同步适配
实现整体下沉到 `dice_ratchet/inference/client.py`，`agent/policy.py` **原样 re-export**
（名字 / 签名 / 行为不变，既有调用方与测试零改动）。

### 2.5 角色解析是鸭子类型，不是 import

MOD-04/06/07 只做 `getattr(obj, "client_for", None)`：注入的是角色提供者就按角色解析，注入的是
普通客户端（测试假件、单角色装配）就原样返回。因此 MOD-07 仍然不 import MOD-03，
`coerce_client(llm, role=...)` 的缺省角色是 `policy`（向后兼容）。

## 5. 附带修复：两处真实接线缺陷（本轮发现）

把三个角色接到真实客户端的过程中发现两处**既有**缺陷 —— 它们此前被单测里的宽松假件
（``**kwargs`` 照单全收）掩盖，因此在任何真实 8B 跑批里都会暴露。两者都直接决定
「六臂对照能不能测出东西」，所以随本轮一起修，并各自补了回归用例
（``tests/unit/inference/test_client_contract.py``）。

### 4.1 `mode` 被写死在 `BackendManager` 上 → 训练局整体降级为启发式

组合根此前一律 `BackendManager(mode="eval")`，而 MOD-04 在**训练局**按 `_llm_mode()`
给出 `train` 口径、探索温度 0.7–1.2。`mode` 过去只在 manager 构造时确定，于是
`validate_sampling(mode="eval")` 对 0.7 直接抛 ``E_LLM_BACKEND_ERROR`` →
`PolicyAgent` 捕获后降级为启发式（``degraded=True``，该局不计入 n）。也就是说：
**训练局的每一次模型调用都不会真正生效**。

修法（MOD-03，两行语义）：``mode`` 可按调用覆盖（`kwargs.get("mode") or self.mode`），
`BackendInferenceClient` 把调用方声明的 train/eval 口径原样带进 manager。效果：

- 评估口（`mode="eval"`）的 B-14 收紧**不变**（temperature 必须 0.0、top_p→1.0、
  top_k→0、seed 必填），有反向用例钉住；
- 训练口（`mode="train"`）的探索温度不再被误判；
- 不传 `mode` 的旧调用口径完全不变（`manager.mode` 仍是默认）。

### 4.2 MOD-07 的提案调用形状与真实客户端不符 → 真实客户端下必然失败

`_call_generate_json` 用的是 ``generate_json(messages, schema, seed=…, temperature=0.0)``，
而统一契约（也是 `BackendInferenceClient` 的形参）是
``generate_json(messages, schema, *, mode, sampling, seed)`` → 缺 `mode`/`sampling`、
多 `temperature`，必然 `TypeError` → `E_EVOLVE_PROPOSE_FAILED`。

同一条路径上还有**消息形状**不一致：MOD-06 反思与 MOD-07 提案传裸 ``dict``，而 MOD-03
的 ``estimate_prompt_tokens`` 取 ``m.content`` → `AttributeError`。修法：

- `_call_generate_json` 改按契约调用（`mode="eval"`、`sampling={"temperature": 0.0}`）；
- `BackendInferenceClient` 在边界处把 `Message` / 同名对象 / 裸 dict 三种形状统一归一
  （`coerce_messages()`），失败时显式报 ``E_LLM_BACKEND_ERROR`` 并给出期望形状。

这两条修完，「真实客户端」路径才算真的接通：提案与反思都能在真实客户端（本地或 API）上跑。

## 8. 本地密钥文件（`.env`）：真实 API 实跑的前置

`export DEEPSEEK_API_KEY=...` 之外，另支持一个**被 .gitignore 忽略**的仓库根 `.env`
（`inference.api_key_file`，默认 `.env`；`""` = 关闭）：

```bash
cp .env.example .env && chmod 600 .env     # 然后把 key 粘到 DEEPSEEK_API_KEY= 后面
```

安全边界（实现见 `dice_ratchet/inference/secrets.py`，用例见
`tests/unit/inference/test_api_key_file.py`，18 例）：

| 性质 | 做法 | 用例 |
|---|---|---|
| 真实环境变量优先 | `lookup_api_key` 先查 `environ`，文件只兜底 | `test_environment_wins_over_file` |
| 只读注册表声明的名字 | 名字来自 `models.yaml` 的 `api_key_env`，其余行永不生效 | `test_lookup_only_returns_the_requested_name` |
| 不能偷改配置 | 只做查找、**从不** `os.environ.update(...)`；文件里写 `DICERATCHET_*` 无效 | `test_lookup_never_touches_process_environment` |
| key 不落盘 | 审计/provenance 只记 `api_key_source`（environment/env_file/missing）与布尔 | `test_audit_records_source_but_never_the_key` |
| 权限提醒 | 同组/其他用户可读 → `llm.api.key_file_permissions` 告警（不阻断） | `test_loose_permissions_emit_warning_event` |

**为什么 `.gitignore` 里那条是硬要求**：`infra.git_ops` 把 `git status --porcelain` 的任何输出
（含未跟踪文件）判为「worktree 不干净」，MOD-07 会因此拒绝演化 —— 没忽略 `.env` 的话，
每次 `evolve` 都会失败。

未登记单价的模型记 `null`（不拿 0 冒充免费）。

## 11. 同 seed 同配置重跑：API 跨时间**不确定**（实测结论）

```bash
# 与 §10 完全相同的配置，只换 run-id（旧 run-id 的 102 条记录原样保留，作为 A 组）
DICERATCHET_EXPERIMENT__ARM=C0 DICERATCHET_INFERENCE__SEED=7 DICERATCHET_EVAL__SEED_TIMEOUT_S=900 \
  .venv/bin/python -m dice_ratchet play --agent llm --seeds train:1000 --mode eval \
  --run-id r-c0-smoke-1ep-det
# exit=0  n=1  win_rate=0.0000  illegal_rate=0.0000  degraded_n=0
.venv/bin/python scripts/compare_api_runs.py r-c0-smoke-1ep r-c0-smoke-1ep-det
```

| | A：`r-c0-smoke-1ep` | B：`r-c0-smoke-1ep-det` |
|---|---|---|
| 调用数 | 102 | 82 |
| status / attempts | 200×102 / 1×102 | 200×82 / 1×82 |
| tokens | 279,695 | 229,039 |
| 成本（高峰档上界） | ¥0.6315 | ¥0.5173 |
| 延迟 p50 / p95 / max | 1004 / 1314 / 1539 ms | 1127 / 1454 / 1610 ms |
| request hash 交集 | — | **9** |
| 其中 response hash 相同 | — | **0**（不同 **9**） |

### 11.1 硬证据：字节相同的请求，9 次全部返回不同响应

两次真跑相隔 9 分 44 秒（首次调用 15:14:39Z vs 15:24:22Z）。这 9 个 `request_hash` 相同，
意味着送给服务方的 **payload 逐字节一致**：同一 prompt、`temperature=0.0`、`top_p=1.0`、
`max_tokens=320`、`response_format=json_object`、`thinking=disabled`，并且
`api_supports_seed=false` ⇒ **seed 根本没进 payload**（所以 request hash 天然忽略 seed 差异）。
唯一变化的变量是**时间**：9/9 返回了不同的 response hash，0 个相同。

> 结论：`deepseek-flash` 在 `temperature=0.0` 下**不保证跨时间确定性**（符合注册表里
> `api_supports_seed=false` 的登记口径）。这不是我们的 bug，而是必须写进实验设计的约束。

### 11.2 文本差异被三级 JSON 管线吸收了一段时间，然后轨迹分叉

- 前 22 个决策的 `decision_kinds` 序列**完全一致**（第 23 个决策起不同）——说明响应文本虽然不同，
  解析出的动作在相当长一段时间里仍落在同一分支。
- 但 `seq_hash` 最终不同：`2cd47d7c…` vs `c828182a…`；A 86 决策 / B 82 决策，
  `illegal_attempts` **13 vs 0**，`battles_won` **10 vs 12**，`illegal_rate` 0.0558 vs 0.0000。
- 调用序列上，前 10 次里 9 次字节相同、第 8 次（index 7）不同，第 11 次起全部不同。
  最可能是「非法动作后的重试 prompt 带上了上一条输出」这类**瞬态**差异（A 有 13 次非法尝试），
  之后两个 run 重新对齐了几次，再彻底分叉。

### 11.3 为什么 `llm.nondeterministic` 没响

该事件由适配器在 `_record()` 里触发，条件是**同一个 run 目录下已存在同 request hash 的记录**。
换了 run-id ⇒ 记录写进另一个目录（`runs/<new>/llm_api/`），自然没有「旧证据」可比。
要让适配器自己裁决，必须**用同一个 run-id 重跑**（旧记录留在原处，适配器会写
`.v2.json` 变体并发 `llm.nondeterministic`）。本次为保住 A 组原始证据没这么做，
改用只读脚本 `scripts/compare_api_runs.py` 做跨 run 比对。

### 11.4 两个必须记住的口径坑

1. **`--run-id` 会改变采样 seed**。`derive_seed("policy", salt, ctx.run, episode, seed, decision,
   attempt, harness_version)` 里含 `ctx.run`（= run_id）。Spec §205 的公式**含 run**，
   MOD-04 PRD FR-04-15 的公式**不含 run** —— 两份文档本身冲突，实现跟了 Spec。
   实际后果：**要复现一次运行的采样流，必须复用同一个 run-id**；换 id 重跑不可能复现。
   （本次能比对，是因为 prompt 模板不含 run_id，payload 才在 9 处逐字节撞上。）
2. **对 A/B/C 对照实验的直接约束**：C 臂 policy 走 API ⇒ 同一配置重跑也会得到不同轨迹
   （本局差到 `battles_won` 10 vs 12）。所以：
   - 单局 `n=1` 的臂间差异**不能**归因于配置（本局胜率都是 0，但内部指标差很多）；
   - paired 对照必须 `n≫1`，且每局用**同一 episode seed** 配对（环境侧照旧确定）；
   - 需要逐位复现时**只能走 replay**（录制字节回放）——这正是 §12 发现的漏洞所在。

### 11.5 花费

重跑 ¥0.5173（高峰档上界）⇒ 本轮真实累计 ≈ **¥1.82**（4 次 probe + A 局 ¥0.63 + B 局 ¥0.52）。

## 12. 顺带修掉的真问题：`api_mode=replay` 回放不出真跑（会静默造假）

### 12.1 怎么发现的

顺着 §11 去读 `_replay_response()`，发现它读 `record.get("response")`；但 `_record()` 落盘的
审计记录**只有哈希、没有响应正文**（`debug_dump_raw` 默认 `false`，`runs/*/prompts/` 是空的）。
原单测 `test_replay_reproduces_recorded_response_without_network` 是**手工把 `record["response"]`
补进去**再回放的 —— 于是 CI 全绿，真实录制文件却回放不了。

后果比"报错"更糟：`_replay_response` 的兜底分支是 `json.dumps(record)`，也就是把**审计 JSON
本身**当成模型输出喂回管线。replay 会"成功"返回，产出一份看起来正常、实则伪造的样本 ——
正是本项目最忌讳的静默错误。

### 12.2 修法（审计记录 v2）

- `_record()` 现在把 `response.text` **原样**落盘为 `response_text`，并记 `response_status`；
  原样而不是重新序列化，replay 的 `response_hash` 才能与原始记录**逐位相等**。
- `_replay_response()` 优先读 `response_text`；遇到只有哈希的旧记录**fail-closed**
  （`E_LLM_UNAVAILABLE`，hint 指出 v1 记录无法回放）；兼容旧的 `response` JSON 体形状。
- 记录 `schema_version` 1 → **2**（字段新增，唯一的读取方是适配器本身）。
- 响应正文只落审计文件（`runs/<run_id>/llm_api/*.json`），**不进 `events.jsonl`**：
  事件保持紧凑，逐字节文本也不会污染按行扫描的确定性检查。
- 测试改成**直接用未修改的录制目录**回放，并断言 live/replay 的 `response_hash` 相等；
  另加「旧 `response` 形状仍可回放」与「缺正文必须 fail-closed」两个用例（`test_deepseek_adapter.py`）。

### 12.3 诚实边界

- A/B 两组已录的 102 + 82 条记录是 **v1（只有哈希）⇒ 不可回放**；可回放性从**下一次真跑**开始。
- §11 证明 API 不确定 ⇒ replay（录字节）是当前**唯一**的逐位复现手段，这个修复是必需的，不是可选优化。
- 未做：同 run-id 真跑一次以实测 `llm.nondeterministic` / `.v2.json` 变体落盘路径
  （单测已覆盖；真跑验证需再花 ≈¥0.5，等确认是否值得）。

## 13. 深门（parity）随机失败的真因：审计把耗时小数当成 seed 泄漏

PR 的深门作业在 `8dd58ac` 上失败，唯一一条：

```
audit leak: verdict=critical exit=2  leak_counts: seed_leak=1
- [seed_leak/critical] log events.jsonl:485 step=484 evidence='isode_s": 2.2083, "event": "'
```

**与本次改动无关，也不是"偶发"**：`dice_ratchet/evals/harness.py:282` 的 `eval.seed_done`
会发 `episode_s`（单局墙钟秒数，4 位小数）。seed 扫描按数字串匹配 3–6 位整数
（`_NUM_RUN_RE`），`.2083` 被切成整段 `2083`，而 held-out 的 forbidden token 恰好是
**2000–2099 / 9000–9099 共 200 个 4 位数** ⇒ 命中即判 critical。`LOG_NON_CONTENT_KEYS`
登记过 `dur_s`/`duration_us`（M1 验收 F3 的 16 条假阳性），但**漏了 `episode_s`/`cpu_s`**
等后加的计时字段。小数部分落不落进区间取决于墙钟 ⇒ **同一提交本地通过、CI 失败**
（误差率约 2%：200/10000）。

修法（`sandbox/audit.py`）：

1. 补齐计时字段白名单：`episode_s`、`cpu_s`、`elapsed_s`、`elapsed_ms`、`wall_ms`、
   `total_timeout_ms`、`seed_timeout_s`；
2. 枚举口径不再靠猜：把 `runs/*/events.jsonl` 与 `runs/*/episodes/**/*.jsonl` 里
   **真实出现过**的「`_s`/`_ms`/`_us`/`_ns` 结尾 + 数值」字段全量扫了一遍，上面即全部；
3. 回归用例 `test_timing_fields_in_events_are_not_seed_leaks`（`tests/unit/sandbox/test_sandbox_audit.py`）：
   用 CI 那条一模一样的 `episode_s: 2.2083` 断言 0 命中，并在同一条事件里把 heldout seed
