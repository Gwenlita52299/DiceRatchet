## 1. 本轮结论（一句话）

`policy` / `reflection` / `proposer` 三个模型角色现在**只由配置决定**：A0/A1/B0/B1/C0/C1 六个臂
可以仅改 `configs/default.yaml`（或 `DICERATCHET_EXPERIMENT__ARM=` / `DICERATCHET_MODELS__*=`
环境变量）切换，业务代码（MOD-04/06/07/08）零改动、且不出现 MLX / llama.cpp / DeepSeek SDK /
HTTP 客户端的直接耦合。切换方式见 README「模型角色与实验臂」小节。缺模型、缺 provider 配置一律 fail-closed，不静默降级。

## 2. 设计决策与理由

### 2.1 DeepSeek 走 `backend: deepseek`，复用 `BackendManager`（而不是另起一套 adapter 栈）

Issue 的架构图写的是 `DeepSeekAPIAdapter`，但现有 MOD-03 已经有完整的「三级 JSON 策略 + schema
校验 + 修复重试 + 上下文守卫 + 内存预算 + 埋点」。如果 API 走平行的一套，就会出现两套语义
（谁负责 schema 修复重试？429 谁重试？usage 谁记？），而 Issue 的验收标准恰恰要求
「429/5xx 错误映射**与本地后端一致**」。

因此：适配器类名按 Issue 要求叫 `DeepSeekAPIAdapter`，但它实现的是 MOD-03 **唯一的 `Backend`
契约**（`load/unload/generate/generate_json/health` + `name/model_id`），注册为
`backend: deepseek`。于是「API 后端」与「本地后端」在 `BackendManager` 眼里完全同形 ——
`execute_json_call()` 在两者上跑同一条修复重试路径（有测试直接验证这一点）。

### 2.2 臂放在 `configs/default.yaml` 的 `experiment.arms`，不另开 `configs/arms.yaml`

- 臂定义因此天然进入 `config_hash` → **换臂即换 run-id 族**（F10），六个臂的产物不会互相污染；
- 环境变量覆盖（`DICERATCHET_EXPERIMENT__ARM=B1`，B-30 的 `__` 分层）无需为新文件再写一套加载器
  （当前 CLI 只有 8 个显式覆盖键，没有通用 `--set`，因此配置层与环境变量就是切臂的两条路）；
- 代码默认值（`ExperimentConfig.arms` 的 `default_factory`）与 YAML 一致，并有单测钉住防漂移。

### 2.3 优先级与「`--model` 不破」

```
experiment.roles.<role>  >  experiment.arms[arm].<role>  >  models.<role>  >  inference.model_id
```

空字符串 = 继承下一层。这条继承规则是刻意保留的：`--model` 写的是 `inference.model_id`，
所以

- A 臂 + `--model mock` → 三角色全是 mock（**离线冒烟的既有语义不变**，这是最容易踩的回归点）；
- B 臂只钉住 `proposer: deepseek-flash`，`--model qwen3-8b-q4` 仍然决定决策/反思模型；
- 配置里显式写 `models.proposer` 或 `experiment.roles.proposer` 才是「明确绑定意图」，优先于 `--model`。

臂是**差分**而非全量声明，正是为了让「继承」在六个臂之间保持可用。

### 2.4 契约下沉（`inference/client.py`）

`InferenceClient` / `BackendInferenceClient` / `coerce_client` 原在 `agent/policy.py`。角色提供者
在 MOD-03，若契约留在 MOD-04，MOD-03 就得反向 import MOD-04（分层倒挂）。因此契约与同步适配
实现整体下沉到 `dice_ratchet/inference/client.py`，`agent/policy.py` **原样 re-export**
（名字 / 签名 / 行为不变，既有调用方与测试零改动）。

### 2.5 角色解析是鸭子类型，不是 import

MOD-04/06/07 只做 `getattr(obj, "client_for", None)`：注入的是角色提供者就按角色解析，注入的是
普通客户端（测试假件、单角色装配）就原样返回。因此 MOD-07 仍然不 import MOD-03，
`coerce_client(llm, role=...)` 的缺省角色是 `policy`（向后兼容）。

## 5. 附带修复：两处真实接线缺陷（本轮发现）

把三个角色接到真实客户端的过程中发现两处**既有**缺陷 —— 它们此前被单测里的宽松假件
（``**kwargs`` 照单全收）掩盖，因此在任何真实 8B 跑批里都会暴露。两者都直接决定
「六臂对照能不能测出东西」，所以随本轮一起修，并各自补了回归用例
（``tests/unit/inference/test_client_contract.py``）。

### 4.1 `mode` 被写死在 `BackendManager` 上 → 训练局整体降级为启发式

组合根此前一律 `BackendManager(mode="eval")`，而 MOD-04 在**训练局**按 `_llm_mode()`
给出 `train` 口径、探索温度 0.7–1.2。`mode` 过去只在 manager 构造时确定，于是
`validate_sampling(mode="eval")` 对 0.7 直接抛 ``E_LLM_BACKEND_ERROR`` →
`PolicyAgent` 捕获后降级为启发式（``degraded=True``，该局不计入 n）。也就是说：
**训练局的每一次模型调用都不会真正生效**。

修法（MOD-03，两行语义）：``mode`` 可按调用覆盖（`kwargs.get("mode") or self.mode`），
`BackendInferenceClient` 把调用方声明的 train/eval 口径原样带进 manager。效果：

- 评估口（`mode="eval"`）的 B-14 收紧**不变**（temperature 必须 0.0、top_p→1.0、
  top_k→0、seed 必填），有反向用例钉住；
- 训练口（`mode="train"`）的探索温度不再被误判；
- 不传 `mode` 的旧调用口径完全不变（`manager.mode` 仍是默认）。

### 4.2 MOD-07 的提案调用形状与真实客户端不符 → 真实客户端下必然失败

`_call_generate_json` 用的是 ``generate_json(messages, schema, seed=…, temperature=0.0)``，
而统一契约（也是 `BackendInferenceClient` 的形参）是
``generate_json(messages, schema, *, mode, sampling, seed)`` → 缺 `mode`/`sampling`、
多 `temperature`，必然 `TypeError` → `E_EVOLVE_PROPOSE_FAILED`。

同一条路径上还有**消息形状**不一致：MOD-06 反思与 MOD-07 提案传裸 ``dict``，而 MOD-03
的 ``estimate_prompt_tokens`` 取 ``m.content`` → `AttributeError`。修法：

- `_call_generate_json` 改按契约调用（`mode="eval"`、`sampling={"temperature": 0.0}`）；
- `BackendInferenceClient` 在边界处把 `Message` / 同名对象 / 裸 dict 三种形状统一归一
  （`coerce_messages()`），失败时显式报 ``E_LLM_BACKEND_ERROR`` 并给出期望形状。

这两条修完，「真实客户端」路径才算真的接通：提案与反思都能在真实客户端（本地或 API）上跑。

## 8. 本地密钥文件（`.env`）：真实 API 实跑的前置

`export DEEPSEEK_API_KEY=...` 之外，另支持一个**被 .gitignore 忽略**的仓库根 `.env`
（`inference.api_key_file`，默认 `.env`；`""` = 关闭）：

```bash
cp .env.example .env && chmod 600 .env     # 然后把 key 粘到 DEEPSEEK_API_KEY= 后面
```

安全边界（实现见 `dice_ratchet/inference/secrets.py`，用例见
`tests/unit/inference/test_api_key_file.py`，18 例）：

| 性质 | 做法 | 用例 |
|---|---|---|
| 真实环境变量优先 | `lookup_api_key` 先查 `environ`，文件只兜底 | `test_environment_wins_over_file` |
| 只读注册表声明的名字 | 名字来自 `models.yaml` 的 `api_key_env`，其余行永不生效 | `test_lookup_only_returns_the_requested_name` |
| 不能偷改配置 | 只做查找、**从不** `os.environ.update(...)`；文件里写 `DICERATCHET_*` 无效 | `test_lookup_never_touches_process_environment` |
| key 不落盘 | 审计/provenance 只记 `api_key_source`（environment/env_file/missing）与布尔 | `test_audit_records_source_but_never_the_key` |
| 权限提醒 | 同组/其他用户可读 → `llm.api.key_file_permissions` 告警（不阻断） | `test_loose_permissions_emit_warning_event` |

**为什么 `.gitignore` 里那条是硬要求**：`infra.git_ops` 把 `git status --porcelain` 的任何输出
（含未跟踪文件）判为「worktree 不干净」，MOD-07 会因此拒绝演化 —— 没忽略 `.env` 的话，
每次 `evolve` 都会失败。

## 9. 真跑纪实：从 401 到 200，以及路上修掉的四个真问题

`key` 填进 `.env` 后按「先 probe、再长跑」的顺序真跑了一轮。这轮实测抓出的东西比离线单测多，
逐条记在这里（含**修正我自己之前的错误结论**）。

### 9.1 401 → 200（认证链路本身是通的）

```
$ python -m dice_ratchet inference probe --model deepseek-flash --mode eval --seed 7 --run-id r-flash-probe4
attempts=1  parsed_ok=true  retry_reasons=[]
prompt_tokens=215  completion_tokens=109  latency_ms≈900-1000  exit=0
```

审计工件（`runs/<run_id>/llm_api/<request_hash>.json`）与 `llm.api.call` 事件同时落盘，字段完整：
`provider/api/model_id/model_revision/online/request_hash/prompt_hash/response_hash/sampling/usage/
cost_estimate/latency_ms/attempts/status/api_key_source`。

### 9.2 问题一：`deepseek-chat` 已下线（注册表是错的）

`GET https://api.deepseek.com/v1/models`（真 key）只返回 `deepseek-flash`（DeepSeek-V4.1-Flash，
1M 上下文）与 `deepseek-v4-pro`。原登记的 `deepseek-chat` 已不在列表内 —— 也就是说，
**离线全绿也拦不住这件事**：注册表里的模型名只有真调一次才能证伪。已改为 `deepseek-flash`，
并顺带登记未被任何臂使用的 `deepseek-v4-pro`（供后续「proposer 能力 vs 成本」对照直接切）。

### 9.3 问题二：flash 默认开思考模式 → 每次都白花一次调用

首次 probe 拿到 `retry_reasons=["JSONDecodeError:$"]`、`attempts=2`，`debug_dump_raw` 的原始转储
显示**第一次的 `content` 是空串**；那条审计记录里 `completion_tokens=256`（正好等于 `max_tokens`）
说明预算被思维链吃光。修法：`api_thinking: disabled`（官方 OpenAI 格式的
`{"thinking": {"type": "disabled"}}`）。实测对比：

| | 输入/输出 token | 修复重试 | attempts | 墙钟 |
|---|---|---|---|---|
| 思考模式（默认） | 895 / 166 | 1 次 | 2 | 3459 ms |
| 非思考（`disabled`） | 215 / 109 | 0 | 1 | 869 ms |

副作用是好的：官方文档明确思考模式**忽略 `temperature`**，非思考模式才生效 —— 正是 B-14
评估口径（`temperature=0.0`）需要的语义。

### 9.4 问题三：审计落盘路径错位（`runs_root` 没传下去）

probe 明明给了 `--runs-root /tmp/dr-real`，但 `/tmp/dr-real/.../llm_api/` 里**一条记录都没有**：
`BackendManager._make_backend` 构造 `DeepSeekAPIAdapter` 时只传了 `infra`/`config`，
适配器于是回落到 `Path("runs")`，把审计写进了仓库根的 `runs/`。修法：`BackendManager(runs_root=...)`
→ 适配器；`RoleModelProvider` 与 `inference/cli._build_manager` 都把已知的 runs 根传下去；
没拿到时记 `llm.api.record_dir_fallback` 事件而不是静默落错地方。已补回归用例
（`test_manager_forwards_runs_root_to_api_audit`）。

**同时修正我之前的错误结论**：§8 里「对 `runs/` 全文检索 key 零命中」当时查的是
`/tmp/dr-*/`（也就是**错位的那个位置**，那里本来就没东西）。key 从未进入任何工件这一结论不变 ——
现在是在**真实落点**（run 目录 + `runs/` + events）上复核的，且 `.gitignore` 覆盖 `runs/`。

### 9.5 问题四：新事件没登记 → 被改写成 `infra.unknown_event`

`llm.api.call` / `llm.nondeterministic` / `llm.api.key_file_permissions` /
`llm.api.record_failed` / `llm.api.record_dir_fallback` 五个事件没进 `EVENT_REGISTRY`，
生产模式下全被改写成 `infra.unknown_event`（dev 模式直接抛 `E_IO_EVENT_UNKNOWN`）。
这是本轮新事件的**规范要求**（events.py 开头：新增事件必须同步本表），已补齐必填字段声明；
复跑后事件流里出现的是 `llm.api.call` 本身，`DICERATCHET_DEV=1` 也不再抛。

### 9.6 成本口径修正：DeepSeek 按人民币、且分时段计价

原字段名是 `cost_per_1k_input_usd`，而官方定价是**人民币**并按高峰/空闲两档（flash：输入缓存未命中
空闲 ¥1/高峰 ¥2 每百万 tokens，输出 ¥4/¥8）。已改为货币中立
（`cost_per_1k_input`/`cost_per_1k_output` + `cost_currency` + `cost_basis`），
登记**高峰档上界**，审计与事件里记 `cost_estimate{amount, currency: "CNY", basis: "peak"}`；
未登记单价的模型记 `null`（不拿 0 冒充免费）。

### 9.7 本轮真实花费

约 8 次调用（含 2 次刻意失败的思考模式探测），单次 215–895 输入 / 109–256 输出 token，
合计 ≈ 4000 tokens ≈ **不到 ¥0.05**（高峰档上界）。这轮没有跑任何长程实验。
