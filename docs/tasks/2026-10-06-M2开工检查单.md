  `d_wall / d_model = 1.02` → **`n_workers` 不缩短总墙钟**，`n` 局墙钟 ≈ `n × 单局模型时间`。
- **单代时间 = 该上限 × 19.6 min**（与候选数 `C`、冒烟 `S`、heldout `H` 无关——它们只决定**怎么花**这个预算）：

  | **100** | **≈33 h** | 更激进的迭代速度；需确认信号量是否足够 |

### D-3 统计功效（n 与重复次数）

- **问题**：两次 n=10 的 CI 上限都只有 **~28%**，而 M3 要坐实 **4–5pp** 量级的增益；MOD-08 已写明
  **n=40 时配对 McNemar 最小可判不一致对数 `k=6`**（k=6 双尾 p=0.031，k=5 p=0.0625）。
- **待定**：`H`（heldout n）最终取多少、是否需要 `n_rep > 1`（`evals.determinism.n_rep_nondeterministic=3`）、
  以及 `evolve.gap_threshold=0.15` / `evolve.win_rate_tol=0.0` 是否需要随新 `H` 重标定。
- **写回**：MOD-08 §13（指标与口径）、Spec §8.6、`configs/default.yaml` 的 `loop.heldout_n` 与 `evals.n_heldout`。
- **注意**：`H` 每 +10 局，按 19.6 min/局 ≈ **+3.3 h/代**——功效与成本必须一起定，不能分开定。
  且加 `H` 会**顶到 D-1 的单代上限**：`H` 变大就得同步抬高 `loop.max_episodes_per_generation`，否则 heldout 臂会被预算挤掉。
  - **⚠️ 本行算术已纠正（2026-10-06）**：`H` 被 `1+C` 支臂各花一次，C=1 时 **H 每 +10 局 = +20 局 ≈ +6.5 h/代**（不是 +3.3 h）；且 H=50 就让 `E_gen=134 > 120` —— **在 D-1 的上限下 H=40 已是最大值**，想加 H 必须先抬上限。

  - **判据换轴（关键结论）**：**M3 的「4–5pp 量级增益」改由 `mean_stages_cleared` 的配对 bootstrap 承担，`win_rate` 降为报告项 + 粗门**。依据：精确配对 McNemar 在真实 `+5pp`（`p01−p10=0.05`）下，每 seed 不一致率 q=0.10 时 **n=40 的 power=0.03**（q=0.05 时 0.01；要 power≥0.8 需 n≈160–640）——即 MOD-08 的「n=40 最小可判不一致对数 k=6」等价于**只能判 ≥15pp**（n=40 下 Δ=15pp→0.57、20pp→0.84）。而 `mean_stages_cleared`（0–6）在 n=40、配对 sd 0.5 / 0.8 下，**Δ=0.30 关（= 6 关制的 5.0pp）→ power 0.97 / 0.66**。故 H=40 对连续指标是够用的，加 H 只对 win_rate 有意义且经济上不可行。

## 3. 必须先做的 2 项实测

### 3.1 【最高风险】full `PolicyAgent` 的 held-out 基线实测（≈3.3 h）

**为什么是阻断项**：MOD-07 的 **C5 门**是 `evolve.max_illegal_rate = 0.05`、`evolve.max_fallback_rate = 0.10`、

  full agent 是 `temperature` 采样 + 工具/记忆/反思全开，**它的非法率既可能更低也可能更高**，必须实测，不能推断。

### 8.2.1 reject 的完整机制（从内核到 `harness/versions/` 一动不动，逐跳可查）

| # | 跳 | 代码位置 | 做什么 |
|---|---|---|---|
| 1 | **内核** | `src/game/kernel/combat.js:460` | 单场战斗 `state.turn > state.config.maxTurnsPerBattle`（=60）→ `state.truncationReason = 'E_KERNEL_TURN_LIMIT'`。**这是游戏规则，不是评测限制** |
| 2 | **沙箱** | `sandbox/api.py::_evaluate_truncation`（L414–429） | 依次判：`self._truncated` → `state["truncationReason"]` → `env_steps >= max_env_steps`（`step_limit`）→ `decision_index+1 > max_decisions`（`decision_limit`）。命中即 `StepResult.truncated=True` |
| 3 | **单局** | `evals/harness.py`（L1100/L1177/L1250） | 决策循环遇到 `terminated or truncated` 即停，`_build_result(truncated=last_step.truncated)` → `EpisodeResult.truncation_reason`（非 None 即被计数） |
| 4 | **聚合** | `evals/metrics.py::truncation_rate`（L444–448） | `sum(1 for r in rows if r.truncation_reason is not None) / len(rows)` → 进 `SplitMetrics.truncation_rate`，即 `ArmResult.metrics` 的那一项。**被截断的局计 lose，但不算 dropped**（`n_dropped=0`），所以 `n_dropped` 那一路拦不住 |
| 5 | **裁判** | `evolve/judge.py` C5 段 | 六条短路链的最后一条。**该行是本复检的焦点**——处置前是三项绝对门，其中 `truncation ≤ cfg.evolve.max_truncation_rate`（**0.15**）在 DeepSeek 臂上必失败。**2026-10-09 处置后（B-45）**：`illegal ≤ 0.35` ∧ `fallback ≤ 0.25` ∧ `truncation ≤ parent.truncation_rate + cfg.evolve.truncation_tol`（**0.05**）。任一项失败 → `_fail("C5", …)` → `Verdict(decision="reject", error_code=E_EVOLVE_ILLEGAL_RATE)`（`judge.py::_fail`） |
| 6 | **落盘 + 编排** | `evolve/generation.py`（L491/L495） · `loop/generation.py::maybe_run_generation`（L172，其中 `state.generation += 1` @L240、`phase="playing"` @L252、成本闸门 `loop.budget_exhausted` @L221） | MOD-07 写 `generations/gen-XXX/{report,decision}.json` 并发 `evolve.decision(decision="reject")`；MOD-06 对**接受与拒绝一视同仁**：`last_completed_cycle`/`generation += 1`、`phase = "playing"`、**退出码 0**（FR-06-7） |

**为什么会「静默」**：第 6 跳里 `reject` **不是错误**，所以 `_call_evolve` 的 `E_EVOLVE_*` 异常分支（→ `error_reject`）不会被走到，`loop.budget_exhausted` 也不会触发（成本闸门只看局数 `E_gen=114 ≤ 120`，与裁决结果无关）。于是一个全拒的闭环会**一路跑完全部代数、退出码 0、日志与事件流都正常**，但 `harness/versions/` 永远是 `.gitkeep`、`artifact_hash` 永远不变。**判定「闭环有没有产出」不能看退出码，只能看 `harness/versions/` 是否出现新版本 + 逐代 `decision` 记录**——这正是 §3.2 判据 1 与判据 4 要查的东西。

**为什么 §3.1 没拦住它**：§3.1 把 C5 的 illegal/fallback/truncation 当作「同一个臂上的三类风险」一起标定（0.3016/0.2146/**0.10**）；但 `truncation` 与前两者**性质不同**——illegal/fallback 是 agent 的**能力/遵从**属性（换臂会大变），truncation 是**局型 × 策略强度**的合成属性（同一 run 里 `random` 0.30、`heuristic` 0.00、8B 0.10、DeepSeek 0.30）。把三类一起按一个臂标定，就必然在换臂时错位。
