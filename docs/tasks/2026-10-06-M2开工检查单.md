  `d_wall / d_model = 1.02` → **`n_workers` 不缩短总墙钟**，`n` 局墙钟 ≈ `n × 单局模型时间`。

### 3.1 【最高风险】full `PolicyAgent` 的 held-out 基线实测（≈3.3 h）

`evolve.max_truncation_rate = 0.05`。而我们目前**唯一的真实 LLM 数据是 `fixed_prompt` 基线**：

  full agent 是 `temperature` 采样 + 工具/记忆/反思全开，**它的非法率既可能更低也可能更高**，必须实测，不能推断。
- **任务**：
  1. 让 **full `PolicyAgent`**（`harness/prompts/decision.md`，`mode="play"`）在 **H1 子集 seed 2000–2009** 上跑 held-out，

### 3.2 小规模端到端冒烟（配合 D-1，半天内可完成）

- **目的**：在投入全量 M2 编码前，确认 **C=1, S=2** 下闭环能真正走完一轮并产出 diff + 决策记录（M2 验收判据）。
- **做法**：MOD-05/06/07 初版可跑后，用最小配置（`k` 小、`H` 小、`C=1`、`S=2`）跑 **1 代**，检查：
  1. **版本机制被真实使用**：`generations/gen-001/{report.json,report.sha256,gate.json}` 落盘且 `decision` 有明确记录（`accept`/`reject`/`rollback`/`pending`）；**若为 `accept`**，则 `harness/versions/vN/` 出现、`version.json.artifact_hash` 非空、`parent` 指向 v0；
  2. `generations.csv` / `report.json` / `report.sha256` 落盘，`generations.csv` 的每代数字可复算；
  3. `audit leak` clean（G4 在 M2 仍需成立）；
  4. 至少一个候选的 gate 判定是**有信息量的**（`condition_trace` 里 C0–C5 逐条带 `value`/`threshold`/`passed`，不是无 trace 的全 accept）。
- **判据（2026-10-09 按用户裁决改写；理由见 §11.3）**：这一步过了才进全量编码；不过则先回头调 D-1/D-2。
  - **合格** = ①–④ 成立 **且机制性失败为零**。**「全部候选被 C1–C5/C2 合法拒绝」也是合格结果**——它证明裁判在工作；parent 在 `medium×6` 已能赢 65–80%，小改动拿不到显著增益本就是**科学结论**，不是缺陷。
  - **不合格** = 出现机制性失败。**判据 2026-10-10 收紧（F47-D）：由「枚举机制错误码」改为「判决口径 + 正向白名单」**，任一成立即不合格：
    1. 该代 `decision="error_reject"`——**基础设施失败的唯一出口**（accept/rollback 抛 `InfraError`；此前它被记成 `reject`，报告甚至写成 `accept`）；
    2. 未捕获异常，或进程退出码非 0；
    3. `error_code` 或任一 chained cause 命中 **`E_IO_*`**（IO/git/落盘/审计类码：一个正常跑完的 run 里不该出现。实测那次的链条正是 `E_EVOLVE_GIT_FAILED` ← cause `E_IO_GIT_DIRTY`）；
    4. `error_code` 是 `E_EVOLVE_*` 且**不在裁判拒绝白名单**内。白名单（只认裁判结论，**正向枚举**）：`E_EVOLVE_NO_GAIN`（C1–C3）、`E_EVOLVE_OVERFIT_SUSPECT`、`E_EVOLVE_COLLAPSE`（C4）、`E_EVOLVE_ILLEGAL_RATE`（C5，含 fallback/truncation 轴）、`E_EVOLVE_GATE_TIMEOUT`（HITL 超时 → rollback）。其余 `E_EVOLVE_*`（`NO_CANDIDATE`/`PATCH_INVALID`/`SMOKE_FAILED`/`PROPOSE_FAILED`/`JUDGE_FAILED`/`GIT_FAILED`/`VERSION_CONFLICT`/`SCAN_FAILED`/`EVAL_FAILED`/`LOAD_FAILED`…）都算机制性失败；
    5. `decision="accept"` 但 `harness/versions/` 没有对应新版本（**幻影 accept**，见 §13 F47-D）。
    **为什么改用正向白名单**：原负向枚举已漏掉 `E_EVOLVE_GIT_FAILED` / `E_EVOLVE_VERSION_CONFLICT`（都不在清单里，且这条路径**退出码为 0**）——死名单会继续漏，与 F45 的教训同向（该死名单已被扩过四次）。正向白名单只要求「裁判结论」这一有限集合，代价是新裁判码必须显式登记。
  - **为什么改写**：原第 1 条硬要「`harness/versions/` 出现新版本」，等于把「候选没赢过 parent」这一**统计结论**记成**验收失败**。实测（干跑）：机制修好后首个真实候选正是以 `C2:no_significant_gain`（`delta=0.0, p=1.0`）被合法拒绝。硬要 accept 会逼着后续去「凑一个能过门的改动」——反向激励。

### 8.2 N2 的复现（本复检的核心证据）

读出来的三个事实（都可直接验证，不需要统计推断）：

3. 同一个候选在 ① 上 `accept`、在 ② 上 `reject` ⇒ **C5 现在判的不是候选退化，而是「你用了哪条臂」**。

### 8.2.1 reject 的完整机制（从内核到 `harness/versions/` 一动不动，逐跳可查）

| # | 跳 | 代码位置 | 做什么 |
|---|---|---|---|
| 1 | **内核** | `src/game/kernel/combat.js:460` | 单场战斗 `state.turn > state.config.maxTurnsPerBattle`（=60）→ `state.truncationReason = 'E_KERNEL_TURN_LIMIT'`。**这是游戏规则，不是评测限制** |
| 2 | **沙箱** | `sandbox/api.py::_evaluate_truncation`（L414–429） | 依次判：`self._truncated` → `state["truncationReason"]` → `env_steps >= max_env_steps`（`step_limit`）→ `decision_index+1 > max_decisions`（`decision_limit`）。命中即 `StepResult.truncated=True` |
| 3 | **单局** | `evals/harness.py`（L1100/L1177/L1250） | 决策循环遇到 `terminated or truncated` 即停，`_build_result(truncated=last_step.truncated)` → `EpisodeResult.truncation_reason`（非 None 即被计数） |
| 4 | **聚合** | `evals/metrics.py::truncation_rate`（L444–448） | `sum(1 for r in rows if r.truncation_reason is not None) / len(rows)` → 进 `SplitMetrics.truncation_rate`，即 `ArmResult.metrics` 的那一项。**被截断的局计 lose，但不算 dropped**（`n_dropped=0`），所以 `n_dropped` 那一路拦不住 |
| 5 | **裁判** | `evolve/judge.py` C5 段 | 六条短路链的最后一条。**该行是本复检的焦点**——处置前是三项绝对门，其中 `truncation ≤ cfg.evolve.max_truncation_rate`（**0.15**）在 DeepSeek 臂上必失败。**2026-10-09 处置后（B-45）**：`illegal ≤ 0.35` ∧ `fallback ≤ 0.25` ∧ `truncation ≤ parent.truncation_rate + cfg.evolve.truncation_tol`（**0.05**）。任一项失败 → `_fail("C5", …)` → `Verdict(decision="reject", error_code=E_EVOLVE_ILLEGAL_RATE)`（`judge.py::_fail`） |
| 6 | **落盘 + 编排** | `evolve/generation.py`（L491/L495） · `loop/generation.py::maybe_run_generation`（L172，其中 `state.generation += 1` @L240、`phase="playing"` @L252、成本闸门 `loop.budget_exhausted` @L221） | MOD-07 写 `generations/gen-XXX/{report,decision}.json` 并发 `evolve.decision(decision="reject")`；MOD-06 对**接受与拒绝一视同仁**：`last_completed_cycle`/`generation += 1`、`phase = "playing"`、**退出码 0**（FR-06-7） |

**为什么会「静默」**：第 6 跳里 `reject` **不是错误**，所以 `_call_evolve` 的 `E_EVOLVE_*` 异常分支（→ `error_reject`）不会被走到，`loop.budget_exhausted` 也不会触发（成本闸门只看局数 `E_gen=114 ≤ 120`，与裁决结果无关）。于是一个全拒的闭环会**一路跑完全部代数、退出码 0、日志与事件流都正常**，但 `harness/versions/` 永远是 `.gitkeep`、`artifact_hash` 永远不变。**判定「闭环有没有产出」不能看退出码，只能看 `harness/versions/` 是否出现新版本 + 逐代 `decision` 记录**——这正是 §3.2 判据 1 与判据 4 要查的东西。

**为什么 §3.1 没拦住它**：§3.1 把 C5 的 illegal/fallback/truncation 当作「同一个臂上的三类风险」一起标定（0.3016/0.2146/**0.10**）；但 `truncation` 与前两者**性质不同**——illegal/fallback 是 agent 的**能力/遵从**属性（换臂会大变），truncation 是**局型 × 策略强度**的合成属性（同一 run 里 `random` 0.30、`heuristic` 0.00、8B 0.10、DeepSeek 0.30）。把三类一起按一个臂标定，就必然在换臂时错位。

### 10.4 根因：MOD-06 的 `EpisodeRunner` 把**一个** `SandboxEnv` 实例交给多个线程并发驱动

```
loop/cli.py:231        env = _make_env(cfg, episode_id=f"loop-{run_id}")      # ← 只建一个 env
loop/cli.py:232        EpisodeRunner(env=env, close_env=False, ...)            # ← 共享它
loop/generation.py:384 evaluate_arm(..., n_workers=cfg.evals.n_workers)        # ← 默认 2
evals/harness.py:300   ThreadPoolExecutor(max_workers=workers)                 # ← 2 个线程
evals/harness.py:1023  env = make_default_env(...)   # 对照：SandboxRunner 在 run_episode 内**每局新建**
```

`SandboxEnv` 是**有状态单实例**（`reset()` 写 `self._state/_env_steps/_decision_index/_illegal_count/...`，`step()` 继续改它们），而 `loop/runner.py` **没有任何锁**。于是两个线程在同一个 env 上交错 `reset`/`step` ⇒
一个线程拿到的 `observation` 可能来自另一个线程刚 `reset` 的那一局 ⇒ 模型按**别的局**的观测（例如地图相位）出动作 ⇒ 语义校验失败 ⇒ 重试 3 次耗尽 ⇒ fallback。这正好解释了「战斗阶段出 `map_choose`」这个特征信号，以及 9× 的非法率与 29% 的 fallback。

**为什么 `play` 没事**：`app.py::_play` 的 `EvalSpec` 把 `n_workers` 写死为 **1**，且 `SandboxRunner` 在 `run_episode` 内部**每局新建 env**。**为什么 `EpisodesConfig`/F26 那条线不是原因**：`loop/cli.py` 确实显式传了 `cfg.env.episode`，难度是对的。

**危害等级**：这会**静默污染每一代的 parent 与 candidate heldout 指标**（无报错、无告警、退出码 0）。在此修复前，§3.2 的判据 1/2/4 与后续 M2/M3 的一切裁决数字都不可信——它比 F28 更靠上游（F28 是门错位，F30 是**被测量的量本身是错的**）。

### 10.5 修复方案（**2026-10-09 已裁决：方案 A**，落地见 §10.7）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | `loop/cli.py` 不再预建 env，改注入 **`env_factory`**（`EpisodeRunner` 已支持该参数，`_resolve_env` 会走 `env_factory(seed, key)` 并负责 `close()`）⇒ 每局一个 env，与 `SandboxRunner` 同构 | 语义最正确、并发真正安全；改动局限在装配层 + 一个回归用例 |
| B | 保留共享 env，但在 `EpisodeRunner.run_episode` 外用互斥锁串行化 | 改动最小，但等于把 `eval_concurrency` 降级为 1（丢失并发收益），且锁粒度容易出错 |
| C | 只把评估的 `n_workers` 设为 1 | 不是修复，只是回避；且会与「`eval_concurrency=2`」的既有口径打架 |
