## 2. P0：必须修，否则硬不变量失效

### P0-1 harness 层混入 `config_hash`，B-19 / T-09-16 在真实使用下必然失败

- 规范：FR-09-3 / Spec B-19——`harness/config.json` 层"计入 `artifact_hash`，**不计入** `config_hash`"，目的是"第一代被接受后 `--resume` 不会冲突"。
- 实现：`load_config()` 把 harness 层 merge 进同一个 base dict（`config.py:760-762`），而 `_canonical()` 只删 `_HASH_VOLATILE_KEYS = {infra.runs_root, infra.log_level, infra.threads}`（`config.py:54-56, 901-907`），因此**任何白名单键的演化都会改变 `config_hash`**。`resolve_run_dir()`（`run.py:192-198`）与 `init_run_dir()`（`run.py:166-172`）随后以该 hash 判定冲突。
- 复现（实测）：

  ```
  gen0         config_hash = acba91ab4e3b5d0a
  harness 把 agent.policy.temperature 0.7→0.95 后
               config_hash = 8d0312a86ea5bd0f
  resolve_run_dir(..., resume=True) -> E_IO_RUN_CONFLICT   # 期望成功
  ```

- 现有测试为何没抓到：`test_resume_tolerates_harness_change`（`tests/unit/infra/test_run_events.py:185-190`）只是**复用同一个 cfg** 再 resolve 一次，从未改动 harness 文件；`test_config_hash_excludes_harness_version`（`test_config.py:126-136`）用两个无关的临时目录比 `artifact_hash`，与配置加载路径无关。两条用例都是空转。
- 修法：`_canonical()` 需要接收"忽略 harness 来源键"的视图（例如 `load_config` 同时返回 `sources`，或维护 harness 覆盖键集合，canonical 时回退到 default.yaml 值）；并补一条真正改 `harness/config.json` 后 `--resume` 仍成功的回归用例。

### P0-2 分层 import 门禁被相对 import 完全绕过；infra 自身违反 NFR-09-5

- 规范：INV-1 / FR-09-15 / NFR-09-5；PRD §12 M0 判定含 `guards check` 通过。
- 实现：`_LayerImportVisitor._check_module()` 只处理 `module.startswith("gamer_rsi")` 的**绝对**导入（`guards.py:241-256`），对 `node.module` 为相对包名（如 `env.selftest`）+ `node.level=2` 的形式直接 return。AST 会遍历函数体内的 import，所以这不是"嵌套漏扫"，而是**相对导入规则缺失**。
- 实测：

  ```
  from gamer_rsi.env.engine import GameEngine  # -> 1 条 E_IO_GUARD_LAYER（detected）
  from ..env.engine import GameEngine          # -> 0 条（漏检，等价越权）
  from ..sandbox.audit import run_audit        # -> 0 条（infra 反向依赖，漏检）
  ```

- 真实后果：**被审代码自己就违反了 NFR-09-5**——`gamer_rsi/infra/cli.py:187` `from ..env.selftest import run_selftest`、`cli.py:291` `from ..sandbox.audit import ...`；而 `python -m gamer_rsi guards check --root gamer_rsi` 输出 `guards: OK — 0 findings`、退出码 0。`gamer_rsi/README.md` 因此写了与事实相反的结论（"依赖单向……由 `guards.scan_layer_imports()` 静态强制（自检通过）"）。`test_scan_self_is_clean` 也随之给出假绿。
- 顺带：`# guard: allow` 只对确定性扫描生效，层门禁 `_report()` 完全不查豁免注释（`guards.py:227-229`），FR-09-15 声明的白名单机制对 INV-1 发现不可用（实测 `# guard: allow E_IO_GUARD_LAYER reason=demo` → `exempted=False`）。
- 修法：`_check_module` 用 `node.level` + 当前文件所在包还原绝对模块名；层门禁接入同一套 `_exemption()`；把 `cli.py` 的 `..env`/`..sandbox` 依赖改为 CLI 薄壳注册（见 P1-12）或在 Spec 明确豁免。

### P0-3 确定性守卫对 `np.random.*` 漏检、对 Spec 认可的 `default_rng(seed)` 误报

- 规范：INV-6 / Spec §8.1（禁止"未显式设 seed 的 torch/numpy 全局随机"）/ FR-09-15。
- 实现：`_BANNED_CALLS`（`guards.py:46-54`）按**字面前缀**匹配 `numpy.random`，`visit_Call`（`guards.py:186-201`）不做别名归一。
- 实测：

  | 片段 | 期望 | 实测 |
  |---|---|---|
  | `import numpy as np; np.random.rand()`（未 seed） | 报 `E_IO_GUARD_RANDOM` | **0 条（漏检）** |
  | `numpy.random.default_rng(seed).random()`（显式 seed，MOD-08 NFR-08-01 指定写法） | 放行 | **1 条（误报）** |
  | `import numpy.random as nr; nr.rand()` | 报 | 1 条 ✓ |
  | `torch.rand(3)`（Spec §8.1 点名） | 报 | 0 条（PRD 未列，另见 P2） |

- 后果：INV-6 门禁在"最常见的 numpy 写法"上双向失效；MOD-08 落地后 `guards check` 会给规范推荐的 `default_rng` 报 4，从而卡住 CI 与演化门禁。
- 修法：建立"局部名→模块名"绑定表（`import numpy as np` / `import numpy.random as nr` / `from numpy.random import ...`），判 `numpy.random.*` 时放行显式带 seed 参数的 `default_rng/Generator`，并显式登记 torch 全局随机规则。

## 7. 修复记录（2026-10-03）

### P0-1 harness 层与 `config_hash` 解耦 ✅

- **改法**：`load_config()` 在合并 harness 层前保存静态基线，并把「harness 覆盖键 → 静态基线值」
  挂到 AppConfig 的私有属性上；`_canonical(cfg, harness_neutral=True)` 在 hash 视图里对这些键
  **回退静态值**（基线不存在的键整键删除）。`config_hash()` 走 neutral 视图，`canonical_json()`
  仍是**生效视图**（供 config.json 快照与 dry-run 复现）。
