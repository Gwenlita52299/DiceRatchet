# MVP1 打通跑（m3r4 之后）与暴露的 3 个版本化/门槛缺陷

> 日期：2026-10-18 · run-id `mvp1` · 分支 `mvp1-rehearsal`（彩排，**已冻结**）·
> 本文回答两件事：①闭环能不能一口气跑完 2 代；②跑完之后 `harness/` 与 git 血缘是否可信。

## 1. 结论

**链路跑通了**：gen-000 基线 → 训练 → 提案 → 静态校验 → 冒烟 → heldout → 裁决 → 版本化 →
落盘，2 代全程无人干预（`hitl=false`）。**但 accept 路径有 3 个缺陷**，其中 2 个会把
`harness/` 的血缘搞脏（已在 §4 修复），第 3 个让 `config_patch` 通道**只能产生字节级变化**
（§5，待裁决）。

| 代 | 候选 | 裁决 | 依据 |
|---|---|---|---|
| gen-000 | — | baseline | 20 局 H3（731080–731099）、`win_rate 0.40`、`harness_v=4` |
| gen-001 | `config_patch` `{"memory.retrieve.top_k": 3}` | **reject** | `C1:win_rate 0.3000<0.3500`（父代 0.40 − tol 0.05，父代heldout 继承自 gen-000） |
| gen-002 | `config_patch` `{"agent.policy.temperature": 0.4}` | **accept** | `0.45 ≥ 0.35`；C2 play_hash 变化；C3/C4/C5 未触发；`decided_by=auto` |

**gen-001 的候选在格式上完全合法**（扁平实际键、白名单内、过加载器），它被拒是因为
**效果**（0.30）而不是语法 —— 正是 F-M3-4（`a1ea2c1`）要的结果。

## 2. 运行现场

```bash
export DICERATCHET_EXPERIMENT__ARM=C1 DICERATCHET_INFERENCE__MODE=eval \
       DICERATCHET_INFERENCE__SEED=0 DICERATCHET_EVOLVE__HITL=false \
       DICERATCHET_LOOP__K=10 DICERATCHET_LOOP__MAX_GENERATIONS=2 \
       DICERATCHET_EVALS__N_HELDOUT=20 DICERATCHET_LOOP__HELDOUT_N=20 \
       DICERATCHET_EVOLVE__HELDOUT_BASKET=H3 DICERATCHET_EVOLVE__MIN_HELDOUT_N=15
caffeinate -i .venv/bin/python -m dice_ratchet loop run \
  --run-id mvp1 --harness-dir harness --seeds train:1030-1049
```

* `config_hash = a192ec6dbea19f6b`；起点 harness v4、`play_hash=sha256:1ebe12e1…`（起点守卫通过）。
* 时长 **3 h 33 min**（08:38:21Z → 12:11:38Z）；LLM 调用 **11,062** 次（全 200）；
  `cost_estimate` 峰值合计 **¥49.66**；prompt 30.94 M tok、命中 11.78 M = **38.09%**（median 36.02%）。
* 实际局数：20 train + 60 heldout + 4 冒烟（heuristic，不花钱）；`memory_version 0→2`。
* **篮子为什么是 H3（20 局）而不是 10 局**：运行期的篮子大小由
  `evals/seeds.py::default_protocol()` 决定（H1=40 / H2=40 / **H3=20**），`configs/seeds.yaml`
  只参与校验与审计；要跑 10 局必须改协议代码。H3 是 D-M3-5 明文允许的彩排篮子（reserve，
  可重复用），代价是 2 倍 heldout 局数。
* `evolve.min_heldout_n` 从 20 降到 15：H3 恰好 20 局，任何一局被 drop 都会让 C0 fail-closed。
* 这只是**彩排**，H3 上 20 局的差异（0.40 → 0.45）在统计上没有信息量，不得当 M3 证据。

## 3. 缺陷 ①：accept 把回滚备份目录提交进 git（P0，已修，修法见 §4）

`versioning.accept()` 先把 `harness/` 全量备份到 `harness/.backup-v{parent}/`，然后
`commit_harness()` 执行 `git add harness` ⇒ **6 个备份文件进了版本提交**（现场：`33f46b5`）。
提交之后 `_restore` 把备份删掉 ⇒ 工作区立刻出现「已提交的文件被删除」的改动 ⇒
**下一次 `loop run` 被 F47-A（`E_IO_GIT_DIRTY`）拦在起跑线**。

## 4. 缺陷 ②：`git_commit` 自引用不可能一次写成（P1，已修）

`version.json` 要记「包含本版本快照的提交 sha」，而这个 sha 只有提交之后才存在。
修复前的做法是提交完**只改写文件、不提交**：

* `harness/version.json` 与 `harness/versions/v{N}/version.json` 永久停在工作区改动里；
* HEAD 里记的是**上一次**提交的 sha（现场：v6 指向 `c8cb74c`＝v5 那次提交），比空值更误导。

修法与 ① 一起（`versioning.py`）：

1. **备份移出仓库**：`tempfile.mkdtemp(prefix="dice-harness-v{parent}-")`，天然不会被提交；
   `infra/git_ops.commit_harness` 再加一层 `:(exclude)harness/.backup-*` 兜住崩溃遗留；
   `.gitignore` 追加 `harness/.backup-*/`。
2. **提交拆两步**（`_stamp_git_commit`）：①快照/工件提交（`tag=False`）；②把回填后的
   `git_commit` 提交一次（`tag=True`）。于是 `harness-v{N}` 指向**回填提交**，
   `git checkout harness-vN` 出来的 `version.json` 自洽；`harness/version.json` 记的是
   **快照提交**的 sha（`ref.git_commit` 同一个值）。
3. 第一次提交里的 `git_commit` 由「父版本的 sha」改为 `""`（提交后回填）——空值好过假值。

`record_rejection()`（D2=A：拒绝也推进版本号、不建快照、不打 tag）和 `rollback()` 同病同治。

## 5. 缺陷 ③：`config_patch` 只能产生「字节级」play 面变化（**待裁决**）

### 5.1 现状（证据链）

1. 被判 accept 的候选是 `{"agent.policy.temperature": 0.4}`（`gen-002`）。
2. 该值在运行期**不生效**：`agent/policy.py:478-484` 规定
   `mode == "eval"` ⇒ `temperature = 0.0`；否则 `clamp(0.7, 1.2, cfg.temperature)`。
   而本轮 `inference.mode=eval`，`_llm_mode()` 对它返回 `"eval"`（**train 与 heldout 都一样**）
   ⇒ 0.4 落在两端都不生效。
3. 但 C2 只看 `play_hash`，而 `play_hash` = 对 `prompts/decision.md` + **`config.json` 字节** +
   `tools/*.py` 取的 sha256（`versioning.py:173`）⇒ 只要 `config.json` 改了一个字节，
   C2 就判「play 面确实变了」。
4. 结果：**「噪音 +0.05」叠上「假变化」= accept**。v6 是一个行为上等价于 v4 的版本。

**同一通道的另一个键也是空的**：`retrieval.top_k` → `memory.retrieve.top_k`，而 agent 的
检索路径显式传 `top_k=policy.memory_top_k`（`policy.py:547`），`memory.retrieve.top_k`
只在 `top_k=None` 时兜底（`memory/store.py:1221`，CLI/诊断路径）⇒ play 面上被遮蔽。

即：当前 `evolvable_keys` 里的**两个键在 play 面上都不改变行为**，`config_patch` 通道
实质上只能产出「C2 觉得变了、实际没变」的候选。这不是 mvp1 的偶发现象，是配置面与
生效面之间缺一层映射。

### 5.2 改进措施（按代价从低到高）

**A. 取值域校验（最小改动，约 1 h）**
给可演化键配「允许区间」，校验器在花钱前拒掉越界值（`temperature ∈ [0.7,1.2]`）。
能挡住 mvp1 这个具体候选，但挡不住「区间内但当前模式不生效」（eval 模式 0.0）。

**B. `play_hash` 用**生效后**的配置（约 3–4 h）**
`play_hash` 计算前先把 `config.json` 过一遍「生效映射」（按 `inference.mode` 归一，
再套 clamp），再哈希。好处：C2 恢复语义——「打法变了」而不是「文件字节变了」；
代价：`play_hash` 同时是**代际继承身份**（臂归档 key）与「同起点豁免」的判据，
换口径会让历史归档失配，需要一次性迁移（或给新口径加版本前缀 `play_hash/2:`）。

**C. 按模式裁剪可演化键（约 1–2 h）**
在装配期按当前 `inference.mode` 过滤 `evolvable_keys`：eval 模式下
`sampling.temperature` 不生效 ⇒ 不进白名单（提案方看不到、校验器拒收）。
实现小、风险低，且直接消除「提案方被引导去写无效键」；但仍不解决「区间内不生效」
的一般情形（只解决按模式可判定的那一类）。

**推荐顺序**：先 **C**（立刻止住无效候选），再 **A**（补取值域），把 **B** 留到
「配置面 ↔ 生效面」的映射表定稿时一起做（B 需要同时处理归档迁移）。
`retrieval.top_k` 的遮蔽问题属于同一类：要么把它改成真正生效的键（让 agent 读
`memory.retrieve.top_k`），要么从白名单里去掉 —— 这是**产品口径**决定，不是实现细节。

## 6. 缺陷 ④：`loop.k` 与 `train.per_generation` 无一致性校验（已修）

训练局的 `generation` 标签是 `state.generation + 1`（F64），而报告里的 `train` 段按
`seeds.take("train", g)` 取数——后者用协议的 `per_generation`（默认 30）。mvp1 用
`k=10` + 种子 1030–1049 ⇒ 第 1 代块（1030–1039）与 `take(1)=1000–1029` **不相交** ⇒
`gen-001.train.n=0`、`win_rate=0.0`，`gain_realism` 建在空集上（提案侧不受影响：
证据束按「最近 N 条」取，不按代取）。

修法：`loop/cli.py::_assert_train_blocks_match_protocol()` 在**跑任何一局之前**逐代比对
「会标成第 g 代的 k 局」与 `take("train", g)`，有偏离即 `E_IO_CONFIG_INVALID` 并给出
「`loop.k` 必须等于 `train.per_generation`」的提示。只改 k、不改协议不再是合法组合。

## 9. 后续：A/B/C 落地 + 白名单换成 eval 侧键（2026-10-18/19，F-M3-9 / F-M3-10）

§5.2 的三个方案都实现了，并在实现过程中发现**第 4 个、也是根因那个**：

| 编号 | 问题 | 修法 | 提交 |
|---|---|---|---|
| D | 候选臂的 `harness/config.json` **从未被读**（只有进程启动时读 run 级那份）⇒ `config_patch` 字节变了、行为一定不变 | `loop.cli._policy_factory` 逐臂 `harness_policy_overrides` → `apply_policy_overrides` | `58e8a62` |
| A | 越界值被 clamp 悄悄改掉 | `EVOLVABLE_KEY_SPECS` 声明取值域，越界 ⇒ `config_value_out_of_range` | `58e8a62` |
| C | eval 下不生效的键仍进白名单 | `effective_evolvable_keys(cfg, mode)` 三重过滤 | `58e8a62` |
| B | C2 只看文件字节 | 新增 `effective_play_hash`（字节 + 生效采样值），C2 要求两者同时变化 | `58e8a62` |
| ⑤ | **换上 eval 侧键** | 白名单改为 `plan.max_plan_len` / `prompt.token_budget` / `policy.retry_max`；`sampling.*` 降级为训练侧 | `01de3b7` |

**⑤ 的根据（mvp2 实测）**：候选写 `agent.policy.memory_top_k: 8`，过校验、C2 生效指纹也变了，
但 heldout 逐局轨迹里 `memory_ids` 全为 null（train 5,146 行有 1,607 行带 memory，heldout
6,134 行 0 行）⇒ 该键对判定指标无效，`0.35 vs 0.45` 是 API 非确定性噪声。
一般化结论：eval 模式下 `temperature`（恒 0.0）、`top_p`（恒 1.0）、`memory_top_k`
（heldout 无记忆）**都不改变判定指标**，`config_patch` 通道必须改用作用在决策路径上的键。

**已知权衡**：`policy.retry_max` 会改变单局调用次数（成本随之变化），比较候选择要留意
成本口径；`plan.max_plan_len` 调小会截断 plan（少动作/回合），是真实行为杠杆。

## 10. mvp4：第一次跑完整判定链（accept，2026-10-19）

参数同 mvp2/mvp3（H3 20 局、k=10、1 代），白名单只剩两个实测 binding 的键。

| 代 | 内容 | 结果 |
|---|---|---|
| gen-000 | v4 在 H3 | baseline，**win 0.30** |
| gen-001 | `config_patch` `{"agent.policy.retry_max": 3}` | **accept**（auto），heldout **0.40** |

完整判定链（第一次走到结束）：

```
C0 heldout.n=20 ≥ 15                              ✓
C1 win_rate 0.4000 vs parent 0.3000 (tol=0.05)     ✓
C2 play 面已变 1ebe12e1→5f237543；生效指纹 d4d2ec13≠c3d3dc65  ✓
C3 win_rate_gap -0.4000 ≤ 0.15                     ✓
C4 collapse_flag=False, entropy_slope -0.00012 ≥ -0.01 ✓
C5 illegal 0.0217 ≤ 0.0692；fallback/truncation 0      ✓
```

**B 与 D 的现场证据**：

* C2 的 `value` 里两个指纹都变了——mvp3 的「生效指纹漏了决策路径旋钮」已修好；
* 行为上 `retry_max 2→3` 立刻可见：第三/四次尝试的步数 2 → 21，重试占比 3.95% → 4.60%。

**诚实边界**：C1 的 +0.10 在 n=20 上 p=0.73（`significant=false`），同一批 seed 的 v4 三次基线
是 0.40/0.45/0.25 ⇒ 这次 accept 的语义是「打法变了且没有判定出的退化」（F62），**不是**
「变强了」。要谈效果证据，n 必须回到 40 以上。

**副作用（已修）**：accept 在彩排分支上建了 `versions/v5/`；切回 main 时 git 不跟踪空目录，
留下 `harness/versions/v5/tools/` 空壳，`next_version()` 按目录名计数 ⇒ 从 5 跳到 6。
