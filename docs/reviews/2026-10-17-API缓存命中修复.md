## 0. 一句话

缓存没有失效；**可缓存前缀只到 `{{observation}}` 之前**。离线复算 `runs/m3-formal` 的
52,224 次 policy 调用：唯一 prompt 命中 **10.8%**、整体 15.7%（被重复调用抬高）、
87.4% 的首次调用命中值**恰好是 256 token**——正是「模板头 + `task.md`」按 64 对齐后的长度。
模板里 1,900 字符的「输出契约」排在动态段之后，永远进不了前缀。

本次补丁做三件事：

1. **把缓存变成一等指标**：`Usage` / `llm_api` 审计 / `llm_calls.jsonl` / 事件 / CLI 都带
   `cache_hit_tokens`、`cache_miss_tokens`、`cache_hit_rate`；
2. **按命中/未命中分价**：注册表新增 `cost_per_1k_input_cache_hit`，`estimate_cost()` 接受
   `cache_hit_tokens`；官方高峰价 **¥0.04/M（命中） vs ¥2/M（未命中）= 1/50**（旧文档按 1/10
   估算，低估了缓存的价值）；
3. **模板静态前置**：新增 `reorder_prompt_cachefirst.py` 与一份 patch / 候选 harness，
   把 `回合预算` + `输出契约` 移到 `{{observation}}` 之前，动态段全部后移，末尾留一句短提醒。

### 3.2 胜率 A/B（cachefix-b0，2026-10-17 23:56，已跑）

run：`runs/cachefix-b0`；候选 `play_hash=sha256:1ebe12e1…`；C1 / hard×6 / eval / seed 0；
H1 40 局；`n=40`、`n_dropped=0`、`degraded_n=0`；6,052 s / 4,653 次调用。对照是
`runs/m3-formal` 的 gen-000 裸 v0（同 40 个 H1 seed）。

| 指标 | 裸 v0（m3-formal g000） | cache-first（cachefix-b0） |
|---|---:|---:|
| `win_rate` | 7/40 = **17.5%** | 7/40 = **17.5%** |
| 配对表 | — | 都赢 2 ｜只候选赢 5 ｜只 v0 赢 5 ｜都输 28 |
| McNemar | — | 双尾 **p=1.0000**（单尾候选更好 p=0.6230） |
| `mean_stages_cleared` | 4.425 | **4.75** |
| `truncation_rate` | 0.10 | **0.05** |
| `illegal_rate` | 0.0318 | **0.018** |
| `fallback_rate` | 0.0018 | **0.0** |
| `mean_decisions` | 124.2 | **109.875**（-11.6%） |
| `mean_battles_won` | 10.975 | **11.9** |
| `mean_hearts_left` | 0.35 | 0.25 |
| 唯一 prompt 缓存命中 | 10.8% | **40.1%** |
| `cost_estimate`（peak 上界） | ≈¥33（旧 40 局口径） | **¥19.74** |

读法：

- **胜率完全相同且配对 p=1.0**：5 个 seed 只在候选赢、5 个只在 v0 赢，方向对半；
  没有证据表明重排伤打法，也没有证据表明它让模型变强。
- 截断（0.10→0.05）、非法（0.0318→0.018）、fallback（→0）、决策数（-11.6%）、战斗数
  （+0.925）都更好；心数略低（0.35→0.25）但没有转化为胜率差。
- 成本：新 run 4,653 次调用 / 12.55M prompt tok / 5.06M 命中；`cost_estimate` 峰值上界
  **¥19.74**，对旧 40 局同口径 ≈¥33 省 **~40%**。实际账户会因空闲时段更低。
- 结论：这是**缓存/成本优化**的 non-inferior 结果（3.7× 命中、约 -40% 上界成本、胜率不变），
  不是“模型变强”的证据。
