## 3. C5 `tol` 的 MDE（本次实测的分母，补充第 1 步的缺省估算）

第 1 步的 MDE 表用的是**缺省估算**（`runs/m2-s32b-smoke-c1-medium6` 一代两臂 80 局）。
本次彩排给了**同口径的本 run 实测分母**（`eval acceptance --sensitivity`，零成本）：

| 轴 | 粒度 | 分母（本次彩排实测） | `tol=0.05` 相当于 | 读数 |
|---|---|---|---|---|
| `illegal` | 步级 | **32,077 尝试** | ≈ **1,604 个步级事件** | 远大于批内噪声 ⇒ 只防真·退化 |
| `fallback` | 步级 | **11,198 决策** | ≈ **560 个** | 同上 |
| `truncation` | 局级 | **94 局** | ≈ **4.7 局** | 仍是**约束轴**（量级最小），但数字被**放大**了 |

> ⚠️ **口径缺陷（F52，仍未修）**：`denominators_from_run` 把 `heldout` **与** `train` 两个 split、
> **所有代、所有臂**的局数**求和**，而 Spec v2.15 / B-72 声明 `truncation` 的分母是
> 「**单臂** 40 局」。本次 run 只有 95 次 `loop.episode_start`（gen-000 20 + gen-001 训练 30 +
> gen-001 评估 44，其中 94 局完整落盘）⇒ 分母报 **94**、`tol` 折合 **4.7 局**，比正确口径（20 局/臂
> ⇒ `tol` ≈ 1 局）**高估约 4.7 倍**。而 §2.3 的 `denominators_source` 仍写「本 run 实测」，
> 读者会误以为它比缺省估算更权威。**M3 起跑前应按轴修正这条口径**（建议：局级轴固定为
> 「该代、单臂、heldout」的局数，并在 notes 里写明用的是哪一代哪个臂）。

## 6. 诚实边界与未修项（F57）

### 6.1 两块产物是「事后补跑」得到的（不得含糊）

`plots/` 的 5 张 PNG 与 gen-000 台账行，是 F56 修复后用**零成本**的
`eval report --generation 0/1` 补出来的，不是 `loop run` 一次跑完就有的。
⇒ 「彩排 6/6 合格」的准确写法是：**「修复 + 补跑两块产物后，6 项判据全部通过」**。
F56 修复后的代码路径（基线 / 代末）已由护栏证明会自己产出它们（下一轮彩排应一次跑完即合格）。

### 6.2 **F57（新发现，未修）**：同一代的 `heldout` 段有两个数字，且台账会被重算覆盖

| 路径 | gen-001 的 `heldout` | 写入产物 |
|---|---|---|
| `loop run`（MOD-07 `_build_report` → `evaluate_generation`） | **parent 的** `n=20 / win_rate=0.10 / truncation=0.15 / mean_decisions=118.05` | `generations/gen-001/report.json` + 当时的台账行 |
| `eval report`（重算） | **候选的** `n=20 / win_rate=0.35 / truncation=0.05 / mean_decisions=135.7` | 覆盖台账同一 `(generation, split)` 行 |

- **根因**：`evaluate_generation` 的契约是 `heldout = winner.metrics if winner else parent.metrics`
  （`evals/harness.py:1202`），而 MOD-07 只在 `decision == "accept"` 时设 `result.winner`
  （`evolve/generation.py:336-337`）⇒ **「候选通过全部门但被 C2 拒」这一代，报告里的 heldout 是 parent 的**；
  而 `eval report` 按 `--arm` 显式取候选 ⇒ 两个路径对同一代给出不同数字。
- **后果（对 M3 判据 1 直接相关）**：判据 1 读的是**台账**。本次补跑后台账里 gen-001 是
  **候选的** 0.35，于是判定器给出 `monotonic_ok=true`；若只看 `loop run` 写的值（0.10），
  结论是 `单调性不成立`（`ci_lo=0.0279 < 0.15−0.02`）。**同一批产物、两个相反结论**。
- **未修原因**：修它要定一条口径（「代际 heldout 到底代表 parent 还是当选候选」），
  而这条口径**直接改变 M3 判据 1 的含义** —— 属需要用户裁决的设计决定，不是我能单方面钉的。
- **建议口径（供裁决）**：代际台账/判据 1 用**parent（该代起点）**，候选的测量归
  `candidates/*.json` 与 `metrics/arms/`（判据 2 用）；这样「单调不降」比较的是
  「每代起点 vs 上一代起点」，语义自洽，且不会被「候选被拒 ⇒ 报告退化成 parent」这一点搞乱。

### 6.3 其它

- `llm.degrade` **12,352 / 12,397 次调用（99.6%）**，`reason=grammar_unavailable`、
  `code=E_LLM_BACKEND_ERROR`。所有 `policy.decision` 的 `source` 仍是 `"llm"`
  （MOD-03 的修复重试把内容救回来了）⇒ 决策是真模型的，但**结构化输出在这一版 provider 上
  几乎每次都走降级路径**，成本与延迟都翻倍。**未立案**（可能是 provider 侧行为），
  但 M3 起跑前值得单独看一次。
- 彩排的 6 项判据里**没有**「成本不超预算」这一项 —— 本轮实测 **¥79.15 vs 估算 ≈¥40（2.0×）**
  而判据全绿。建议把「实测成本 vs 估算」写进彩排脚本的输出（不进判据，但必须显式打印）。
- `run` 目录 `runs/_sweep/m3-rehearsal/` 是**草稿区**（`runs/` 被 ignore）；H1 的 5 个残局
  证据以 [F54 事故记录](2026-10-11-M3彩排事故记录-F54.md) 的 sha256/尺寸/判决形式登记，
  原始草稿目录已删（同 run-id 重跑需要它不存在）。
