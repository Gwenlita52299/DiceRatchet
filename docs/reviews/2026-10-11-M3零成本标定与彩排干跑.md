## 0. 一句话结论

**能零成本做完的两块都做实了，并且各修掉一个「形式通过、实则没跑」的缺陷**：

1. `scripts/run_m3_calibration.sh --free` **修复前是假通过**：退出码 0，但 ② 一步没跑
   （配置装配就抛 `E_IO_CONFIG_INVALID`，被 `|| echo` 吞掉）。修复后实测 **20 局 H3 启发式基线落盘、6.07 s、¥0**。
2. `scripts/run_m3_rehearsal.sh` 有**同一处**死锁（`loop run` 直接退出码 2）——彩排从未跑过，所以此前没暴露；
   同一提交一并修掉，`--plan` 与 `loop run --dry-run` 现在都能走通。
3. `eval test --check` 三例行为正确（0 / 1 / 1），**未创建存证、事件里 0 条解锁记录**。
4. `eval acceptance --sensitivity` 同时产出 `acceptance` 与 `tol_sensitivity` 两块，**总是退出 0**。
5. `rehearsal check` 在真实（不完整）run 上给出**逐项可解释**的结论：6 项里 1 项不合格
   （`metrics/arms/` 无臂归档），并实测证明「机制性失败为零」这条判据**是活的**（注入反例即被抓住）。

**诚实边界（不得省略）**：

- **彩排本身没有执行**（≈2 h / ≈¥40；`loop run --agent llm` 一次都没跑过）。
  本报告证明的是「彩排**可执行**、判据**已代码化且是活的**」，**不是**「彩排已合格」。
- **阈值仍未标定**：C5 的三个 `tol`（`illegal` / `fallback` / `truncation`）与 `c1/c2/c3/c4` 的阈值

  **没有**用实测抖动回填任何阈值。

#### 2.1.3 根因与修法

- **根因（一处配置口径，两个受害者）**：`infra/config.py::Config.validate()` 有跨段一致性检查

  阶段抛错（连 `baseline` 这种完全不看 heldout 的命令也一样）。
- **修法**：两个脚本各补一行 `export DICERATCHET_LOOP__HELDOUT_N=20`（并写明为什么必须成对改）；

  「**已存在**（`baselines/heuristic-heldout.json` 在案 ⇒ 跳过；`archive_baseline` 是**不可覆盖归档**，
  重跑只会多留一份 `-<ts>.json`）」与「**失败**（⇒ `set -e` 出真退出码）」分开。
- **提交**：`de090d8 fix(scripts): F51 —— 两个 M3 脚本的 heldout 死锁 + --free 吞掉失败`
  （提交信息内含修复前证据与诚实边界）。

## 3. C5 `tol` 的 MDE 表（三轴）

**分母来源**：本表用 `scripts/run_m3_calibration.sh --free` 第 ① 步的**缺省估算**
（= `C1` 在 `runs/m2-s32b-smoke-c1-medium6` gen-1 上**一代两臂 80 局**的实测口径），
`rates = {illegal: 0.0318, fallback: 0.0017, truncation: 0.30}`；
落盘副本：`runs/_sweep/m3-calibration-tol-sensitivity.json`。

| 轴 | 粒度 | 分母（来源） | `tol=0.05` 相当于 | 相当于几个 se | 一句话读数 |
|---|---|---|---|---|---|
| `illegal` | **步级** | **27,836 尝试**（缺省估算；一代两臂 80 局，实测） | **≈ 1,392 个步级事件** | **≈ 48 se**（`se≈0.0011`） | 门只抓「真·退化」：要漂 1,400 个非法步才触发，**不承担**检微小漂移 |
| `fallback` | **步级** | **9,021 决策点**（缺省估算；同上） | **≈ 451 个步级事件** | **≈ 115 se**（`se≈0.0004`） | 比 `illegal` 更钝（分母更小、实际发生率更低）；同样是防真·退化 |
| `truncation` | **局级** | **40 局**（缺省估算；**单臂** heldout，粒度 `1/40 = 0.025`） | **≈ 2 局** | **≈ 0.69 se** | **约束轴**：2 局抖动就能触门；`truncation` 是三个 `tol` 里唯一真正吃紧的那个 |

**不可互换**：把三个 `0.05` 当同一个数字读会得出相反结论——对前两轴「门太松」，对第三轴「门就是噪声」。
⇒ M3 里 `truncation` 的 `tol` 与 backstop 必须单独论证，不能拿 `illegal`/`fallback` 的松紧类比。

**同一工具在「本 run 实测」分母下的样子**（证明分母来源确实分优先级，而不是写死的字符串）：

| run | `denominators_source` | `illegal` | `fallback` | `truncation` | 读法 |
|---|---|---|---|---|---|
| `m3-freecheck`（合成：2 代 × 2 臂 × 10 局 heldout + 10 train = 40 局） | 本 run 实测 | 8,600 尝试 ⇒ 430 个 | 3,670 决策 ⇒ 183 个 | **40 局 ⇒ 2 局** | 分母随 run 变化，读数跟着变 |
| `m3-calibration`（真实：一代 20 局启发式） | —（无台账，`eval acceptance` 拒绝：`E_IO_STATE_MISSING`，见 §5.3） | — | — | — | 纯基线 run 没有 `generations.csv` |

## 5. 诚实边界与主动发现（不得当成已修结论）

### 5.1 彩排未执行、阈值未标定

- **彩排本身没有执行**：本轮 `loop run --agent llm` **一次都没跑过**（`--plan` 与 `--dry-run` 不付费、不落盘）。

  🟡「脚本与判据已就绪并实测（`--plan` 通过、17 条用例）；**彩排本身未跑**」。
  本报告只把 🟡 里「已就绪并实测」的那半做实（并且顺手补了「脚本本来跑不起来」这个洞）。
- **阈值仍未标定**：`illegal_tol=0.05` / `fallback_tol=0.05` / `truncation_tol=0.05` /
  `truncation_backstop=0.60` 与 `c1=-0.010`、`c2=0.60`、`c3`（`0.01`/`0.05`）、`c4=0.50`、`confirm_generations=2`
  **仍是「起点值 + 待回填」**。本报告做的是**MDE 换算**（这根门能分辨多大漂移），
  **不是**用同代内抖动标定出来的值——后者需要 ≥2 代配对实测，当前归档数据不支持（`c2` 结构上要 ≥2 代，
  而归档里只有 1 个 run 有 2 代）。
- **本报告里的所有数字都是「启发式/合成」口径**：`heuristic` 基线（20 局）与合成 run（10 局/代）
  **不能**当作 `C1` 的强度或方差锚点。尤其 §2.3 那例的 `win_rate=0.3 / mean_stages_cleared=5.1`
  是**启发式在 hard×6 的 H3 上**，与 `C1` 不同源。
- **本轮无逐字节复现证据**（D-M3-3 裁决 A）：`C1` 是 API 臂，本报告也不宣称任何可复现性结论。

### 5.2 合成 run 的性质（为什么必须说清）

`runs/_sweep/m3-freechecks/runs/m3-freecheck` 是**合成**的：用 `/tmp/mk_synth_run.py` 生成
30 个 heldout 局（`gen-000` 10 局 parent + `gen-001` 10 局 parent + 10 局 `cand-synth0001`，
**全部落在 H3 731080–731089**）与 10 个 train 局（`1000–1009`），**没有**跑游戏引擎、**没有**调模型。
它的用途只有两个：① 给 `eval test --check` / `eval acceptance --sensitivity` 一个「不污染仓库 `runs/`」的现场；
② 给 `rehearsal check` 一个「真实代码路径产出、但确实不完整」的 run，好让 6 项判据各自表态。

它的**统计量没有任何科学含义**：`monotonic_ok=true`、`P(gap>0)=0.9991` 是构造出来的，不是实测结论。

### 5.3 `F52`（新发现，未修）：`denominators_from_run` 的实测分母跨代跨臂求和

- **现场**：`eval acceptance --sensitivity` 在合成 run 上把 `truncation` 的分母报成 **40 局**
  （10 局 heldout 的 2 代 parent/候选 + 10 局 train = **40 个 `EpisodeResult`**），
  而该模块自己的 docstring 与 Spec v2.15 / B-72 声明的是「`truncation` = **单臂 40 局**」。
- **根因**：`dice_ratchet/evals/tol_sensitivity.py::denominators_from_run` 对
  `("heldout", "train")` 两个 split 的**全部** `EpisodeResult` 逐局累加（`episodes += 1`），
  既不分代、也不分臂。合成 run 上恰好是 40（**数字对、口径错**，所以更危险）；
  在真实 M3 run（3 代 × 2 臂 × 10–40 局 + train）上会把分母**放大到数百**，
  于是 `truncation` 的「tol 相当于几局」被系统性**高估**。
- **方向**：按 Spec 的声明，局级轴应固定为**单臂、该代**的 heldout 局数（或显式取 `max(臂)`），
  并在 `notes` 里标注用的是哪一代哪个臂。
- **为什么本轮不修**：改口径要连带 `tests/unit/evals/test_evals_acceptance*.py` 与
  Spec §11.1m 的 B-72 条目，属独立改动；本轮的任务边界是「零成本标定 + 彩排干跑」。
  ⇒ 登记在此，建议作为 M3 起跑前的**第 2 步**小修（¥0）。
- **它不影响本报告 §3 的表**：§3 用的是 `--free` 第 ① 步的**缺省分母**，那条路径不经过 `denominators_from_run`。
- **⚠️ 2026-10-15 已修（Spec v2.33 / B-91）**：实测分母改为读 `metrics/arms/` 的**同一代两臂**（步级 = 两臂合计尝试/决策，局级 = 每臂局数），并改用实测 `rates`；`eval acceptance --sensitivity` 的 payload 增 `measured_comparison` 写明哪一代哪几臂。**补一条更硬的证据**：正式实验（`m3-formal`）的日志印出 `truncation 382` 与「≈19 局（粒度 1/382）」，而**同一个 JSON 的 note** 写着「2 局 / 分母 40 局」；今天拿同一份归档重算是 **462**（分母随 run 长度漂移）。修复后同一 run（gen-003 两臂 28,330 尝试 / 9,754 决策 / 每臂 40 局）读数回到「≈2 局（分母 40 局，粒度 1/40）」。

### 5.4 `F53`（新发现，未修）：`eval report` 的重算路径把 train 段退化成 6 个键

- **现场**：合成 run 的 `generations/gen-001/report.json` 里 `train` 段只有
  `{low_confidence, n, n_dropped, win_rate, window}`；同一份台账的 train 行因此写成

  ```
  1,1,0,train,,10,0.5,0.0,0.0,,,,,,,,,,,,,,,,e69000158f78ce80,de090d8,2026-10-11T05:07:05Z
  ```

  ⇒ `ci_lo=ci_hi=0.0`、`mean_stages_cleared / hearts / battles / decisions / illegal / fallback /
  truncation / entropy` **全为空**。
- **根因**：`evals/cli.py::cmd_eval_report` 先把 train 局聚合成完整 `SplitMetrics`，
  但传给 `render_report_sections(...)` 时用的是**缩水摘要**（只有 n/win_rate/low_confidence/…），
  于是 `report["train"]` 丢掉 rich 字段；`harness.generations_rows_from_report()` 从
  `report["train"]` 取列 ⇒ 全部取空。**生产路径（MOD-07 `_finish_report`）不受影响**，
  所以真实 run 的 train 行是满的——这条路只在 `eval report` 重算时退化。
- **影响**：`eval report` 重算出来的台账，其 train 一侧**不可用于任何连续指标**；
  `win_rate.png`/`train_heldout_gap.png` 的 train 曲线只有 `win_rate` 一个数（无 CI、无 n 之外的量）。
  而 `rehearsal check` 的判据 3 只数**行**、不查**单元格**，所以**这条退化不会被彩排发现**。
- **方向**：把完整 train 指标段一并传给 `render_report_sections`（或让 report 的 train 段与
  MOD-07 同形），并给 `rehearsal check` 的判据 3 加一条「train 行至少 `mean_stages_cleared` 非空」。
- **为什么本轮不修**：同上，属独立改动；且它**不阻塞**本报告的任何 DoD 项。

### 5.5 其它现场（不是缺陷，但读者需要知道）
