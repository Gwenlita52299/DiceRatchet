## 5. 判据 1 的轴：四组实测的噪声底（本轮最有价值的科学结论）

| 测量 | 何时 | `win_rate` | `mean_stages_cleared` | 说明 |
|---|---|---|---|---|
| gen-000 基线 | 10-13 15:51Z | 0.175 | 4.425 | harness v0 |
| gen-001 起点 | 10-13 21:18Z | 0.100 | 4.250 | **同一份 v0、同一批 40 seed** |
| gen-002 起点 | 10-14 03:24Z | 0.150 | 4.150 | 同上 |
| gen-003 起点 | 10-14 09:42Z | 0.100 | 4.325 | 同上 |
| **极差** | — | **0.075（7.5 pp）** | **0.275 关** | — |
| `heuristic` 基线 | 10-14 17:48Z | 0.325 | 4.975 | 对照：**高于全部四组** |

> **补充（v1.3，F66 之后）**：三次「候选」臂的测量**也是同一份 v0**（补丁从未进入 prompt）⇒ 同一份 harness 在同一批 40 seed 上共有 **7 次独立测量**：`win_rate` = 0.175/0.100/**0.125**/0.150/**0.225**/0.100/**0.150** ⇒ 均值 0.1464、SD 0.041、**极差 12.5 pp**；`stages` 极差 0.325 关。「候选组」均值 0.167 vs parent 组 0.131（Welch t=+1.00）⇒ **两组不可区分**。

**为什么这件事最重要**：判据 1 的通过条件是 `ci_lo(g) ≥ win_rate(g−1) − 0.02`（或 `P(gap>0) ≥ 0.90`），
而「同一份 harness」的两次测量之间就能差 **7.5 pp**（CI 宽度本身 ≈15 pp）⇒
**这个判据在 n=40 上不可判**：任何真实的小幅改进都会被噪声吞掉，任何「单调不降」的通过/不通过
都可能是抽签结果。F57 的 `not_applicable` 豁免**只是在「harness 没变」时避免了这个坑**，
一旦真有 accept（harness 真变了），判据 1 立刻回到「7.5 pp 噪声 vs 4–5 pp 效应」的不可能三角。
⇒ M3 的结论必须写成「**判据 1 在当前 n 与当前臂下不可判**」，并把主判定量交给
`mean_stages_cleared`（同样四组的极差是 0.275 关，明显更稳，与 D-3 的功率分析方向一致）。

## 6. 本轮抓出的结构性缺陷（每条都有留痕）

> **2026-10-14 追加**：**F58 / F59 / F60 已修**（Spec v2.25 / B-82；见每条末尾的「✅ 已修」段，含 before/after 实测）。其余条目仍待裁决。

### F58（🔴 高）`audit leak` 的 `future_room_leak` 是**跨局误报**：派生集合并 + 全局扫描

- **现场**：`audit leak --split train` ⇒ `verdict=critical exit=2`、
  `leak_counts: future_room_leak=5852`（findings 记录 200 条，按 episode 去重后集中在 3 个 heldout 局的
  `e-731000/731001/731002` 各臂）。样例：`episodes/heldout/e-731000-g000-parent.jsonl:74`
  `evidence='","nodeId":"n-03-2-0"},"reward":'`。
- **根因**：`derive_hidden_tokens(run_dir, split="train")` 把**整批 train 局**的「未揭示行节点」
  **并成一个集合**，而 `log` 面扫描（`audit.py` 的 `if "log" in surfaces`）遍历

### 9.2 C2 的阈值：名义 α=0.05，n=40 下的**等效阈值**远高于此

- **（改判前口径继续）名义定义**：`C2 ⟺ paired.significant == True 且 direction == "up"`（MOD-07 §8.2），

| 代 | 候选 / parent 胜 | b | c | 精确 McNemar p | 判定 |
|---|---|---|---|---|---|
| 1 | 5/40 vs 4/40 | 5 | 4 | **1.0000** | 不显著 |
| 2 | 9/40 vs 6/40 | **7** | 4 | **0.5488** | 不显著（最接近） |
| 3 | 6/40 vs 4/40 | 6 | 4 | **0.7539** | 不显著 |

### 9.3 为什么 n=40 不够：噪声分解 + 「要多少局」

用**四组同 harness（v0）、同 40 seed** 的 parent 归档，把噪声拆成两块
（σ_w = 同一 seed 重复测量之间的抖动 = API 不可复现性；σ_b = seed 之间的真实异质）：

| 轴 | σ_w（重复测量） | σ_b（跨 seed） | 单次测量总 SD |
|---|---|---|---|
| `mean_stages_cleared` | **1.015 关** | 0.679 关 | 1.221 |
| `mean_hearts_left` | **0.718** | 0.346 | 0.797 |
| `win_rate` | **0.529** | 0.237 | 0.580 |

**σ_w > σ_b** ⇒ 噪声的主要来源**不是 seed 差异，而是 API 的不可复现性**（D-M3-3 裁决 A 的实测代价）。
配对差值（候选−parent）的实测 SD：`Δstages` **1.236–1.456 关**、`Δwin` **0.474–0.519**——
几乎全部由 σ_w 贡献（`√2·σ_w ≈ 1.44`）。由此：
- **有效样本量只看「每臂总局数 E」**：`SE ≈ σ_w·√(2/E)`（40 局 ⇒ SE≈0.23 关，与实测 CI 半径 0.45/1.96 吻合）。
  ⇒ **「把 H 从 40 加到 80 个 seed」与「同 40 个 seed 重复测 2 次」在统计上等价**（都只是把 E 翻倍）；
  也就是说**加 seed 不是唯一的路，重复测量同样有效**（当前 `n_rep=1`）。
- **要达到 80% 功效判定 0.30 关**：`E ≈ (2.8×σ_w/0.30)²×2 ≈ **180 局/臂**`（现为 40）⇒ ×4.5。
  按实测 ¥0.52/局：每代评估 +280 局 ≈ **+¥145/代**（3 代 ≈ +¥435），墙钟 +≈7 h/代。
- **便宜的替代（按性价比排序）**：① 把 C2 的判据轴固定为 `mean_stages_cleared`（σ_w 相对效应最小，
  已在本轮数据里成立）；② 把 `n_rep` 从 1 提到 3（**同 seed 重复**，直接砍 σ_w 的有效贡献，
  比加 seed 便宜且不消耗新 seed 预算）；③ 用**过程轴**做前置门（`illegal`/`fallback` 是**步级**、
  分母 ≈12k/≈3.7k ⇒ C5 三轴的样本量是**局级的 300 倍**，能判 0.05 的漂移——这正是 C5 已经做到的，
  而 C2 的局级轴做不到）；④ 把「接受」改成**噪声感知的棘轮规则**（例如：过程轴不退化 + 结果轴方向为正
  且 Δstages > 0.5×CI 半径，连续 K 代确认），代价是要改验收语义。

### 9.4 API 缓存：命中率实测与结构性上限

- **现状**：`llm_api/*.json` 的 `usage` **只有 `prompt_tokens` / `completion_tokens`，没有任何 cache 字段**
  ⇒ **命中率目前在产物里根本不可测**，而 `cost_estimate` 一律按**高峰 + 未命中**计价（`basis: "peak"`）。
- **实测（用调用时刻反推）**：52,319 次调用里 **32.7% 落在高峰时段**（北京时间 9–12 / 14–18）。
  全按高峰+0 命中 = ¥344.44（注册表口径，与实际估算一致）；**按实际时段、仍 0 命中 = ¥228.61**；
  **账户实际扣减 ¥197.67 ⇒ 比「按时段、0 命中」低 13.5%**。若命中输入价为未命中的 1/10，
  **隐含整体输入命中率 ≈17.8%**。
- **结构上为什么低**：`harness/prompts/decision.md` 的占位符顺序是
  `{{task}} → {{harness_version}} → {{tools}} → **{{observation}}** → {{legal_actions}} → {{reflections}} → {{memory}} → {{constraints}} → 输出契约`。
  前缀缓存要求**稳定的前缀**，而：
  - **第一个动态占位符之前只有 ≈263 tok**（模板头 84 + `task.md` 179），占平均 prompt（**2,784 tok**，p50 2,824、p90 3,204）的 **≈9.4%** ——这是**理论可命中上限**；
  - **最大的静态块（「输出契约」≈510 tok）排在全部动态内容之后** ⇒ **永远不可能命中**；
  - ⇒ 动态部分 ≈2,011 tok（**72%**）**每次都在变**（观测 1,500 上限 + legal_actions + 反思 + 记忆 900 预算）。
- **重新设计的四个动作（按预期收益排序）**：
  1. **重排模板**：静态块（头部 + `task` + **输出契约** + 工具签名 + `harness_version`）全部前移，
     动态块（observation / legal_actions / reflections / memory / constraints）全部后移。
     可命中前缀 263 → ≈773 tok（**9.4% → 27.8%**），预估省 **≈15–20%** 输入费，**零架构改动**。
  2. **把缓存变成一等指标**：MOD-03 记录 `prompt_cache_hit_tokens` / `miss_tokens` 与 `cache_hit_rate`，
     注册表加 `cost_per_1k_input_cache_hit`，`cost_estimate` 按命中/未命中分价（现在 `basis: peak` 会系统性高估 ≈1.7×）。
  3. **砍动态段的绝对量**（这才是大头，72%）：观测渲染上限 1,500 tok → 用**状态增量/摘要**
     （仓库里已有 `dice_ratchet/env/digest.py`）替代整份投影；`legal_actions` 已压缩过一次（19,633→1,939 tok），
     仍可只送「与上次不同的部分 + 合法动作的**索引**」。
  4. **换决策架构（对 Q2 也有效）**：让启发式先产出 3–5 条候选 `plan`，LLM 只做**排序/选择**
     （prompt 从 2,784 tok 降到数百 tok，且把「C1 弱于启发式」的问题一并修掉——
     §3.4 的基线显示 `heuristic` 0.325 / 4.975 关全面优于 `C1`）。

### 9.5 与「运行顺序」有关的两个新发现

#### F64（🔴 高 → ✅ **2026-10-14 已修**）训练局的 `generation` 记的是 **cycle 序号**，导致报告的 `train` 段**永远筛不到那 30 局**

- **现场**：轨迹里 `split="train"` 的三块训练局，`generation` 分别是 **0 / 1 / 2**（seeds 1000–1029 / 1030–1059 / 1060–1089），
  而它们产出的是 **gen-001 / gen-002 / gen-003**（差 1）。
- **后果（机制，逐行对得上）**：`evaluate_generation(g)` 的 train 段是
  `load_episode_results(root, "train", generation=g, harness_version=parent.harness_version, seeds=train_window(g))`
  ⇒ 用 `generation=g` 去筛，命中的只有**本代的冒烟局**（`parent-smoke` 2 + `cand-*-smoke` 2，恰好 4 局、`win_rate=0.0`），
  **30 局真实训练局一局都进不来**。实测台账：gen-1/2/3 的 train 行 `n=4`（三行一致）。
- **影响面**：台账的 `train` 行、`train_heldout_gap.png`、以及 **C3 的 `win_rate_gap = train − heldout`**
  全部建立在 **2 个 seed × 2 个臂 = 4 局**上（分辨率 ±0.25）。F-M3-3 的本意是「`train_window(g)` 的滚动窗口（默认 60 局）」
  ——**代码里写的是 60 局窗口，实际拿到 4 局，且不报错、不告警**（静默降级成「4 局的 train 曲线」）。
- **附带**：gen-000 那 30 局训练（`generation=0`，`train_window(0)=[]`）**从未进入任何报告**；
  `cycle N` 与 `gen-(N+1)` 的错位也让任何按 `generation` 聚合的读者（含我 v1.0 的盘点表）容易写错。
- **候选修法**：训练局落盘时写**它服务的那一代**（`cycle+1`），或给轨迹加 `cycle` 字段并在聚合时显式换算；

  **不许静默退化成 4 局**。

#### F65（🟠 中 → ✅ **已由 D-M3-7 解决**，2026-10-14）parent 每代都被重测一次 —— 本次为**同一份 v0** 付了 4 次

- **现场**：gen-1/2/3 各自重新测了 parent 的 heldout 40 局（01:33→03:21 / 07:05→08:59 / 13:03→15:15），
  加上 gen-000 基线，**同一份 harness v0、同一批 40 个 H1 seed 被完整测了 4 次**（160 局 ≈ **¥83**）。
- **机制**：F57/B-78 的「parent 测量跨代继承」**只在上一代 `decision == "accept"` 时才生效**
  （`_inherited_parent_arms` 的四条资格）；本 run 三代全 `reject` ⇒ 资格不成立 ⇒ 每代重测。
- **两面性（必须写清）**：这 4 次重复**是 §5 那个「噪声底 = 7.5 pp」结论的唯一来源**——

  （建议：把重复测量变成**显式设计**——例如每代固定 `n_rep=2` 只对 parent 臂，既保留噪声底又不重复 40 局）。

### 9.6 F66（🔴🔴 最高优先级 → ✅ **2026-10-14 已修**）：候选补丁**从未进入决策 prompt** —— ⑤ 与 ⑧ 实际是同一次测量

> **触发**：用户追问「⑤ parent heldout 40 与 ⑧ 候选 heldout 40 之间有什么区别？」

**按设计，两者只应差一个变量**：篮子（H1 40 局）、seed 集合、`split=heldout`、评估温度 0.0、
`n_workers=2`、`memory_version`（快照）、局配置（hard×6，`episode_config_hash` 两者相同）**全部相同**；
唯一应当不同的，是 ⑧ 用的是 `generations/gen-00N/staging/<id>/prompts/decision.md`（v0 + 本代 6 行补丁），
⑤ 用的是 `harness/prompts/decision.md`（v0 原件）。**实测：两者没有任何区别。**

**证据（三条，互相独立）**：
1. **首个决策点的 `prompt_hash` 逐字节相同：40/40 个 seed**（`prompt_hash` 是对**完整 messages**的摘要，
   模板文本在内——若模板含那 6 行，step 0 就该不同）。
2. 整臂 `prompt_hash` 集合：parent 4776 个 / 候选 4393 个 / **交集 320 个**；首个分叉步中位数 **8**
   （即两条轨迹**动作**首次分歧处），**step 0 从无分歧**。若模板不同，交集必须是 **0**。
3. 三次「候选」测量与四次 parent 测量放在一起看（见 §5 补充）：**7 次都是同一份 v0**，
   `win_rate` 极差 **12.5 pp**，候选组与 parent 组 **不可区分**。

**根因（代码级，两行）**：
- `evals/harness.py:849`：`executor = runner or _default_runner(harness_dir=harness_dir, ...)`
  —— **一旦注入 `runner`，`harness_dir` 参数完全不参与策略构造**；
- `evolve/judge.py:538-540`：MOD-07 给**每一次候选评估**都注入 `EvalRunnerAdapter(loop 的 EpisodeRunner)`，
  而后者的 `policy_factory` 是 `loop run` 起跑时用 **run 级 `harness/`** 建好的
  （`loop/cli.py::_policy_factory(..., harness_dir)`）。
  ⇒ `staging_dir` 被传进 `evaluate_arm`、被记进臂归档 provenance（`harness_version=0`、`episode_config_hash` 相同），
  但**从未到达 PolicyAgent**；`resolve_path("harness/prompts/decision.md", harness_dir=staging)` 的探测路径
  `staging/harness/prompts/decision.md` 不存在，于是回落到 cwd 的**未打补丁**模板。

**影响（本 run 与历史结论）**：
- 本 run：**判据 2（可归因提升）没有任何数据**；「0 accept」不是「补丁无效」，而是「**补丁从未被测试**」；
  三次 C2 拒绝在「被比较的两个东西其实是同一个」的意义上**形式正确、内容空洞**；
  `evolve.smoke/evolve.evaluate` 记录的 n/win_rate 也全部是 parent 的又一次测量。
- **同一代码路径 ⇒ 历史结论待复核**：`loop run` 下的**所有**候选测量都受影响，
  包括 **M2 §3.2 冒烟的「候选 +5.07 pp、合法拒绝」** 与 **M3 彩排的「候选 0.35 vs parent 0.10」**
  （后者当时被写成「差的是那一次补丁」）。
- **不受影响**：`eval ablation`（`run_ablation` 不注入该 runner）、`eval report` 的重算路径、M1 的基线（无候选）、
  以及本 run 的 **gen-000/各代 parent 测量**（它们本来就是 v0）——§5 的噪声底结论因此**更强**（7 次而非 4 次）。
- 附带解释：所谓「API 不可复现的噪声」里，有一大块其实是「**同一份 harness 的两次独立采样**」；
  F66 让 §9.3 的 σ_w 估计更保守（它把两次配置测量当成了重复测量）。

**候选修法（三选一 + 一条必需护栏）**：
1. 让 runner 感知 per-arm harness_dir：`EvalRunnerAdapter` 携带 `arm → harness_dir` 映射，
   或 `EpisodeRunner.run_episode` 增加 `harness_dir` 覆盖参数；
2. 或候选评估**不注入** loop 的 runner，直接 `_default_runner(harness_dir=staging_dir, ...)`；
3. **护栏（必须，最便宜）**：`evaluate_arm` 把**实际加载的模板 `template_hash`** 写进臂归档 provenance，
   并由 MOD-07 断言「候选含 `prompt_patch` ⇒ 其 `template_hash` ≠ parent 的」，
   不满足即 fail-closed（`E_EVOLVE_*`）。**这条护栏会让 F66 在 30 秒内现形**；
   它同时是本次教训的一般化：**"工件被正确 staging" 不等于 "工件被真正使用"**——
   上一版同类教训是 F55/F56（「函数存在但没有调用点」「台账写了一半」）。

**诚实边界**：本条**不追回**已花的 ¥197.67，也不改变「判据 1 `ok=false`」（三代确实 0 accept）；
它改变的是「这批数字能支持什么结论」——**本 run 不能再用来回答「补丁有没有效」**，
M3 的判据 2 必须**修复 F66 之后重跑**才有数据。
