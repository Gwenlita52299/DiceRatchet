## 1. P0：按现文实现会直接失败或使结论无效

### P0-1 MOD 系列和 GAME 游戏模型整体脱节
- **现状**：
  - Spec §4.2 的 Observation（`self_hp/self_block/floor/dice: list[int]`）和 §4.3 的 6 个动作（`place_die/levelup_choose`…）仍是旧游戏的。
  - GAME 实际的状态是 `hearts/virtue/ward/stage/chapter`、骰面带学派和魔化，动作有 18 种（`play_face/discard_die/purify/map_choose/shop_*/event_choose/…`）。
- **波及面**：
  - MOD-01：`EpisodeConfig`、`FullState`、`Action`、奖励表、`configs/enemies.yaml`。
  - MOD-02：`OBSERVATION_SCHEMA`，以及蜜罐注入点 `floor_plan_json/shop_state/levelup_options`，这三个在 GAME 状态里都不存在。
  - MOD-03：`ACTION_SCHEMA`。
  - MOD-04：LLM 输出 schema 和启发式里的"击杀/格挡/最大伤害"。
  - MOD-05：`SituationKey`（`floor_bucket/hp_bucket/slot_kinds`）和 tags 枚举。
  - MOD-08：`KIND_SPACE` 固定为 6，熵归一化分母是 `log2(6)`；主指标 `mean_hp_left/mean_kills/floors`。
- **影响**：各模块照现文实现，彼此的数据结构无法和游戏本体对接。INV-7 规定的"环境原生主指标"在 GAME 里也没有对应字段：GAME 用的是 hearts、到达关数，没有 HP 和楼层。
- **建议**：
  - 裁决 P-29，以 GAME-00 §9.4 的 `obs-1.0.0` 为游戏侧基准，由 MOD-02 定义 agent 侧投影 `obs-agent-1.0.0`。
  - Action 枚举直接引用 GAME-01 §4 的分派表。
  - INV-7 主指标改为 `outcome`、`stage_reached`、`hearts_left`、`battles_won`。

### P0-2 步数上限和 GAME 局长不兼容
- **实测**：`src/game/tests/golden` 里 4 组完整对局分别是 218、313、482、259 步。
- **各 PRD 的上限**：

  | 位置 | 值 |
  |---|---|
  | MOD-06 `loop.max_steps_per_episode` | **120** |
  | MOD-08 `eval.max_steps` | **60** |
  | MOD-07 C5 `max_mean_turns` | **60** |
  | MOD-01 `max_steps` / `max_turns` | 1000 / 200 |
  | GAME-01 `maxTurnsPerBattle` | 60（这是单场战斗的回合数，不是整局步数） |

- **影响**：
  - 按 MOD-08 的默认值，每一局 heldout 评估都会在第 1～2 关被截断，`win_rate` 恒为 0。
  - MOD-07 的 C5 把"回合"和"步"混用，会误伤正常对局。
- **建议**：先定义"一局"的粒度（整局 10 关 / 单章 / 单场战斗，见 P0-3），再用同一个配置键推导所有上限。"步"（`steps`）和"回合"（`turn`）必须分开命名。

### P0-3 算力预算不可行
- **估算**（8B，MOD-03 p50 1.5 s/步，每局约 300 步，不含重试和反思）：约 **7.5 分钟/局**。
- **单代工作量**：训练 30 局，加上 MOD-07 的 parent heldout 40 局，再加 3 个候选 × (冒烟 5 + heldout 40) 局，共 205 局，约 **25.6 小时/代**。
- **总量**：M3 要求 ≥3 代，再加基线（3 × 40 局）、消融（3 臂 × 40 局）、test（100 局），合计约 **4～5 天**的连续推理。
- **冲突**：MOD-08 NFR-08-05 要求"n=40、4 worker、≤20 分钟"。但 MOD-03 规定 `max_inflight=1`（P-10），40 局串行需要约 5 小时，二者矛盾。
- **建议**：
  - 在 Spec §8.6 增加成本模型：每局步数 × 每步延迟 × 每代局数。
  - 考虑以下降本手段：
    - 把"一局"缩短为单章（3 关，约 90 步），或者训练局用单章、评估局用整局。
    - 评估模式在 temperature=0 下是确定的，parent 的评估结果可以按 `(harness_version, seed)` 缓存，不必每代重跑。
    - 冒烟局改用启发式预筛。

### P0-4 评估温度三方冲突（按现文会导致评估局全部降级）
| 位置 | 评估温度 |
|---|---|
| MOD-03 FR-03-07 | `mode="eval"` 要求 `temperature ≤ 0.3`，越界**抛 `E_LLM_BACKEND_ERROR`** |
| MOD-04 FR-04-15 | `eval_temperature = 0.7`，**不可被覆盖** |
| MOD-08 §9 | `eval_temperature: 0.0` |
- **影响**：
  - 按现文，MOD-04 在评估局的每一步都会被 MOD-03 拒绝，然后走全局 fallback，该局被标 `heldout_degraded`，不计入评估样本。结果是整个 heldout 评估没有有效样本。
  - 即使统一成 0.7，MOD-08 的 G3（报告逐字节可复现）也无法成立。
- **建议**：评估统一用 `temperature=0.0` 加显式 seed，写入 Spec §8；删掉 MOD-04 里"不可覆盖 0.7"的表述。"防确定性窥探"只对训练局有意义。

### P0-5 重试和非法计数的语义自相矛盾
- **重试叠加**：MOD-03 `generate_json` 内部会做首答加 2 次修复（3 次调用）；MOD-04 在外面又有 `retry_max=2`（3 次尝试）。一步最坏要 **9 次 LLM 调用**。
- **非法计数**：MOD-04 FR-04-10 按"每次尝试"累计 `consecutive_illegal`，阈值是 3。
  - 一步里 3 次尝试都失败，就直接判负。
  - 因此 FR-04-14 的"重试耗尽 → 启发式 fallback"**永远走不到**：§8 伪代码在 fallback 之前就已经 `return lose`。
  - 每次尝试都调用 `reject()` 扣 -0.05，一步最多扣 -0.15。
- **重复计数**：连续非法在 MOD-01 FR-01-11、MOD-04 FR-04-10、MOD-06 FR-06-1 三处**各自判负**，口径还不一致（MOD-06 只数第三级执行非法）。
- **建议**：
  - 语法修复只在 MOD-03 做，不计为非法。
  - MOD-04 只负责语义层重试，`consecutive_illegal` 按**决策步**计。
  - 判负只由一个模块负责（建议 MOD-01，因为它是环境原生结果），其他模块只读 `info`。

### P0-6 MOD-02 的受限执行方案不可行
- **资源限制**：`run_harness_callable` 在主进程里设 `RLIMIT_AS=256MB` / `RLIMIT_CPU`。这两个限制作用于**整个进程**，而主进程同时持有 5.6～18.8 GB 的模型权重。
  - 按现文实现，第一次调用工具就会触发 OOM 或被 SIGXCPU 杀掉进程。
  - Python 线程无法被强制终止，所以 T 用例里"线程被清理"做不到。
- **AST 白名单缺节点**：`ALLOWED_NODES` 缺少运算符和控制流节点，包括 `Add/Sub/Mult/Eq/Lt/Gt/And/Or/Not/USub/Break/Continue/In/NotIn`。
  - 于是任何写了 `a + b` 或 `x == y` 的合法 `rank_actions` 都会被判违规。
  - `gate()` 是 fail-closed，结果是 **tool_patch 这条演化路径实际上全部失效**。
- **import hook**：`install_agent_import_hook()` 设计为"不可卸载"并拒绝 `dice_ratchet.env.*`。但 `SandboxEnv` 在同一进程里也要 import env，这里自相矛盾。
- **建议**：
  - harness 工具统一放到**常驻子进程 worker** 里执行，用 JSON 管道通信，在子进程上设 rlimit，超时就杀掉并重启 worker。
  - AST 改为"黑名单节点 + 白名单调用"，或者补全运算符节点，并加一个正例测试："含四则运算和比较的工具必须通过"。
  - import hook 改为按调用方模块路径判定，或者在安装 hook 前先 import env。

### P0-7 MOD-09 的两处设计会破坏运行
- **redaction 毁坏轨迹**：
  - T-09-7 把 `"seed": 2042` 擦成 `"<REDACTED:seed>"`，但轨迹 schema 要求 `seed` 是 integer，于是 heldout 轨迹全部校验失败。
  - MOD-08 的配对检验恰恰需要 heldout 的 seed。
  - 文件名 `episodes/<seed>.jsonl` 本身就暴露了 seed，擦内容没有意义。
  - INV-5 约束的是 **prompt 和 memory**，不是审计侧的轨迹。
  - **建议**：redaction 只作用于 prompt/memory/reflection 这几个出口；轨迹保留原值，只在 agent 可见的路径上做扫描。
- **resume 必然失败**：FR-09-3 让 `config_hash` **包含** `harness_version`，FR-09-5/12 又要求 `--resume` 时 `config_hash` 一致，否则报 `E_IO_RUN_CONFLICT`。一旦某一代的候选被接受，`harness_version` 变化，之后的 `--resume` 就会被拒。
  - **建议**：拆成两个哈希。`config_hash` 只覆盖静态配置，用于判定 run 身份；`artifact_hash` 覆盖 harness，按代记录在 report 里。

## 3. P2：逐模块问题

### MOD-01 env-rules
- 头部已经声明"规则以 GAME 为准"，但 §4～§9 的正文全部是旧规则，容易误导实现者。建议整体重写为「GAME 内核的 Python 等价移植 PRD」：
  - 保留工程契约：`GameEngine` 门面、错误码映射、golden 对拍、覆盖率门槛。
  - 规则部分只引用 GAME-01。
- FR-01-10 奖励内部用定点整数，返回 float；和 GAME-01 K-3"内核无浮点"之间的边界需要说明：奖励应放在内核之外计算，这与待定项 4"奖励归 MOD-08"一致，建议直接采纳。
- 失心语义：GAME 是 virtue 归零时扣 1 心，心数归零才判负。FR-01-05 的"玩家 hp≤0 → lose"需要改掉，对应 P-30。

### MOD-02 env-sandbox
- `SlotView.constraint` 的类型写成 `"any"|"odd"|"even"|"min:N"`，其中 `min:N` 不在 DSL 文法里，DSL 用的是 `ge:N`。
- 投影耗时 NFR ≤200 µs 按旧状态估算，GAME 的 obs 大得多：带地图、骰池、遗物。需要重新估。
- FR-02-5 在 import 时读 `docs/prd/OBSERVATION_CHANGELOG.md`，这让运行时依赖文档目录；打包后就会失效。建议版本号常量放在代码里，由 CI 校验两者一致。

### MOD-03 inference
- 整体扎实：降级契约、内存预算公式、错误码表都很清楚。只需修 P0-4 和 P1-19。
- `BackendManager(BuildManagerFacade)` 里的父类 `BuildManagerFacade` 没有定义，应该是笔误。
- Q-1（M1 只做 MLX）已经登记为 P-24，与 §15 的工作量表不一致，需要同步。

### MOD-04 policy
- FR-04-15 采样 seed 取 `derive_seed(..., step_index, ...)`：同一步的重试是否换 seed 没有写。不换的话，重试在温度 0 下会得到同一输出，重试没有意义。
- 格式鲁棒性矩阵第 2 行说"允许剥离一层 markdown 围栏再解析"，期望结果却写成 `E_ACTION_PARSE`，自相矛盾。
- 启发式 fallback 需要按 GAME 规则重写。建议直接复用 `src/game/scripts/bots.js` 里 `greedy_counter` 的逻辑（它在三个难度上都达到了目标通关率），并由 MOD-08 的 heuristic 基线共用同一份。

### MOD-05 memory
- **确定性缺陷**：`created_at/expires_at/last_ref_at` 取墙钟时间。即使调用方固定 `now`，两次重跑写入的 `created_at` 也不同，所以 Recency 和 TTL 不同，G3 不成立。
- **淘汰失效**：`min_age_days=7` 且 `ttl_days=90`，而一个 run 只有若干小时，所以没有条目会满 7 天。**所有条目都免于淘汰**，容量上限永远不起作用，最终会触发 `E_IO_MEMORY_QUOTA`。
- 两个问题的共同建议：时钟改为逻辑时钟，用"训练局序号/代数"（如 `age_episodes`、`ttl_generations`）。
- 效用分依赖 `adopted`，而它由"动作 kind 和 hint kind 一致"判定；GAME 里大多数步都是 `play_face`，这个判定几乎恒为真，需要更细的粒度（如学派/槽位）。

### MOD-06 loop
- `E_LLM_BACKEND`（加载失败）会直接中止 run，而 MOD-03 规定先换 `fallback_backend` 重试一次、再降级。需要对齐。
- FR-06-5 的周期触发条件 `len(completed) % K == 0` 和 §8 伪代码 `cycle > prev` 是两种写法，以伪代码为准。
- `reflect_context_window=5` 要求传入最近 5 局的摘要，但摘要由谁生成、是什么格式都没有定义。

### MOD-07 evolve
- **验收可以退化满足**：M3 要求"≥3 代且 heldout 主指标单调不降"。C1 的 `tol=0` 加上 C2 要求 n=40 时配对显著（MOD-08 自己在 §8.2 也承认功效不足），实际结果很可能是**每代都拒绝**，而这样恰好满足"单调不降"。建议 M3 追加两条："≥1 次 accept"和"报告接受率"。
- `smoke_seeds=train:1000-1004` 每代都用同一组，而这正是第 1 代训练用过的 seed；它的比较基线 `parent_smoke` 在 §8.1 伪代码里也没有计算。
- `better(cr, winner)` 没有定义。§8.2 写的"C2 delta 最大、candidate_id 最小"需要落到伪代码里。

### MOD-08 evals
- **T-02 的手算值有误**：`0.811278 / log2(6) = 0.313845`，PRD 写的是 `0.313852`，按 1e-6 容差测试会失败。T-01（Wilson）和 T-03（JSD）我已复算，是正确的。
- FR-08-10 把 dropped 局（超时/崩溃）排除出 n，会产生幸存者偏差：agent 在难 seed 上崩溃反而能提高胜率。建议 dropped 计为负，或者单独报告。
- 验收 3 要求"test 胜率的 Wilson 下界 > 最好基线的点估计"。参考 `src/game` 的 bot 数据：medium 难度启发式约 35%，n=100 时要超过它，胜率需要约 45% 以上。门槛可以保留，但应在计划里明确这个预期。

### MOD-09 infra
- 根目录 `.gitignore` 目前只忽略了 `src/game/runs/`。如果训练链路的 `runs/` 放在仓库根目录而没有被忽略，`worktree_clean_check()` 每次都会判定为 dirty，演化永远被阻断。需要把 `runs/` 加入忽略。
- `JsonlWriter` 把 `run_start` 写到 `episodes/run.jsonl`，和 `episodes/<seed>.jsonl` 共用目录，MOD-08 按 glob 读轨迹时会误读。
