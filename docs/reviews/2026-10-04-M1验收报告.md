**为什么 `fixed_prompt` 只跑 n=10（2026-10-04 追加，依据 F22）**

先按协议跑了 H1 全量 n=40，**跑到 18% 时主动终止**：
- 实测每局平均 **245–266 次 LLM 调用**（env 步口径，分布重尾：最短 132 步，已见超 700 步仍在跑的局），而不是成本模型假设的 ~79 次（决策点口径）——`_agent_loop` 每推进一个 env 步就问一次模型（F22）；
- 按实测 ~15 次调用/分外推，**n=40 需 ~12.3 h 连续推理**（排期原估「40 局 ≈ 4 h」，低估 3×）；
- 已完成的 3 局**全部 lose**（seed 2000/2001/2002），当时点估计 0%；但**这个初步读数偏悲观**——n=10 子集跑完后是 **1 胜 / 9 有效局（11.1%）**，仍显著低于 `heuristic` 的 40%，但**不是零通关**。（教训：3 局不足以判断一个 ~10% 量级的通过率，见 §13.3 第 5 条。）

因此改用 **H1 的前 10 个 seed（2000–2009）**，并**把 `random` / `heuristic` 也重跑到同一组 seed**（`runs/m1-real-h1n10/`），三者严格同源可比；全量 n=40 的 `fixed_prompt` 与「按决策点调用」的修正（F22）一起推迟到 M2 开工前。原 n=40 运行的 3 局证据保留在 `runs/m1-real-h1/`（未入库，数字已摘录到本节与 F21/F22）。

### 13.3 流程建议（本次实测的最大教训）

1. **「权重落盘 + 一次真实冒烟」必须是里程碑的退出条件，而不是验收后的追加动作。** M1 的 MOD-03/04/08 在「全假模块 + 假后端」下全绿，却在真实 `mlx-lm` 上**完全跑不起来**（F14–F16）。建议 CI 增加一个最小真实样本作业（如 5 条 prompt 的 `inference probe/robustness`），失败即红。
2. **配置项必须有「被消费」的守门测试。** 本次一口气发现三个死配置/死参数：`baseline --seeds`（F8）、`evals.seed_timeout_s`（F20）、`agent.policy.fixed_prompt_path`/`task_path`（F12）。M0 已因同类问题（`episode.toggles`）记过一次 F1。
3. **探针与被测对象必须同源。** `probe`/`bench` 的固定 prompt 与生产 prompt 不同源，曾把「提示词欠约束」误报成「模型格式鲁棒性差」（F16）。
4. **长跑前先算清「调用次数 × 单次延迟」，并确认口径**（决策点 vs env 步）。本次 `fixed_prompt` 的 12.3 h vs 排期 4 h 的差距，一半来自 `t_d` 低估、一半来自 F22 的粒度错误。

### 14.3 F20：`seed_timeout_s` 真正被消费（两道闸）

1. **协同预算**（第一道，确定性）：`SandboxRunner.run_episode(timeout_s=…)` 把
   `time.monotonic() + timeout_s` 作为 deadline 传给两个循环，每个决策点前检查；超预算即
   收尾为 `dropped=True` + 新增错误码 **`E_EVAL_TIMEOUT`**（`outcome` 强制 lose），
   按 Spec §8.5 计 n 并按 lose 计。
2. **硬看门狗**（第二道，兜住「worker 完全不看预算」）：`run_eval` 以
   `seed_timeout_s + 60 s` 为上限巡检（0.5 s 粒度），超限即放弃该 future、记 dropped，
   **并换一个新的线程池继续跑剩下的 seed**——否则 `n_workers=1` 时一个卡死的 worker 会让
   其余 seed 永远排不上队（这正是 F20 描述的「eval 永久挂起」）。收尾用
   `shutdown(wait=False)`，绝不 join 被放弃的线程。

**残余风险（如实登记）**：Python 无法杀死已运行的线程，被放弃的 worker 会一直留着（由 MOD-03
的调用级 `generate_timeout_ms` / `total_timeout_ms` 保证最终收尾）；且 `ThreadPoolExecutor`
的线程非 daemon，`concurrent.futures` 的 atexit 钩子会在解释器退出时 join 它们。因此
**第三道闸仍是 MOD-03 的调用级超时**，本层只保证「本 run 不会被一个 worker 拖死」。

**证据**：`tests/unit/evals/test_evals_longrun_guards.py` 的 4 条用例（runner 侧消费预算、
PolicyAgent 循环同样受约束、硬看门狗放弃挂起 worker 后仍完成全部 seed 且两者都记 dropped、
预算充足时不误报），以及 `test_abandoned_pools_are_not_joined`（放弃后必须 `wait=False`）。

### 14.15 本轮新发现 **F23（P1：`plan` 契约不完备 → 成本 ×2.3、25% 决策点退化为启发式）**

**怎么发现的**：F22 修好后第一次真实 n=40 跑批（`runs/m1-real-h1n40/`，跑了 25 分钟后被我主动
停掉——原因见下），逐事件统计发现单决策点的后端调用数是 **2.29**，而不是预期 ~1.07：

| 指标（`runs/m1-real-h1n40/events.jsonl`，79 个决策点） | 实测 |
|---|---|
| 后端调用 / 决策点 | **2.29**（181 次调用 / 79 决策点） |
| 决策级尝试 / 决策点 | **1.28**（101 / 79） |
| **重试耗尽 → 启发式兜底** | **20 个决策点 = 25%** |
| JSON 首答通过率（MOD-03 侧） | 89.6%（17/164 次首答 `E_LLM_SCHEMA_INVALID`） |
| 非法动作的具体形态 | 全是 `play_face` 的 `{dieId, slotId}` 配对不在当时的 `legal_actions` 里 |

**根因**：`decision.md` / `fixed_v1.md` 的输出契约只写了「所有 id 必须逐字来自观测或可选动作」，
**没有说 `play_face` 的 `dieId` 与 `slotId` 是一个不可拆的配对**，也没有说「同一个 `plan` 内不得
重复使用同一 `slotId`/`dieId`」。于是模型很自然地「从观测 `hand` 里挑一张骰子 + 从 `slots` 里挑一个
槽位」自行组合，而 `_execute_plan`（FR-04-8）会逐个动作用**当时的** `legal_actions()` 重新校验 →
任一动作失效就让**整个决策**作废重试；连续 3 次耗尽即 `reject(final=True)` → 启发式兜底，
并按 MOD-02 的 `policy_failure_streak` 记账。

**受控对照（证明这不是模型能力问题，而是契约问题）**：同一份代码、真实沙箱，只把 LLM 换成一个
「逐字照抄 `legal_actions` 里的配对、同一 plan 内 `dieId`/`slotId` 不重复」的假客户端：
`illegal = 4 / 329 env 步`（1.2%）、`calls/决策点 = 1.07`、`fallback = 0`（见 §14.1 的 T-22）。

**修复分两步**（每步都有真实模型的对照证据）：

**第一步（第 6/7 条）**：两条模板（`harness/prompts/decision.md`、`gamer_rsi/agent/prompts/fixed_v1.md`）
**对称**补上：

> 6. 动作必须逐字取自 `legal_actions` 的整条记录（尤其 `play_face`：`dieId` 与 `slotId` 是一个配对，
>    必须照抄出现过的组合，**不要**自己把 `hand` 里的骰子与 `slots` 里的槽位组合起来）。
> 7. 同一个 `plan` 内不得重复使用同一 `slotId`/`dieId`；`use_ability` 只能用于还有次数的能力。
>    每个动作执行前都会用当时的合法动作重新校验，**任一动作失效会让整个决策作废重试**。

**第二步（第 8 条，真正的最大头）**：只读 A/B 诊断（同一批 24 个真实 `player_turn` 观测、
`temperature=0`、`max_attempts=1`，只改模板文本）发现**首答 schema 失败率 29%（7/24），且全部是
`ValidationError:$.plan[N].targetId`** —— 模型把可选字段填成 `null`，而 schema 只接受字符串 id
（`additionalProperties:false` + `targetId: {type: string}`；不能改成 `["string","null"]`，那会让
`compile_grammar()` 直接返回 `None`，毁掉 GBNF）。补一条：

> 8. **可选字段不需要时直接省略**：`targetId` 这类可选字段在不需要指定目标时整条不要写，
>    更不要写 `null`、`"null"`、`""` 或 `-`——它们不是合法 id，而且会让整条 JSON 校验失败。

补后同一批样本的首答 schema 通过率 **71% → 92%**（失败 7/24 → 2/24）。两次改动都**对称**落到
两条模板上是刻意的：只改一侧会让基线与 harness 的提示词强度不可比，M3 的「相对基线增益」就失真
（这正是 F21 要防的混淆）。`harness/version.json` 的 `reason` 已记这两次修正（仍是 v0，未演化）。

**配套的续跑闸升级**：`baseline --resume` 的「测量协议」由常量细化为

### 14.16 本轮新发现 **F24（P1：`seed_timeout_s` 是墙钟预算，被 `n_workers` 共享放大后把整批判成 dropped）**

**怎么发现的**：F23 契约修好后的第一次 n=40 跑批（`runs/m1-real-h1n40d/`）跑完的头两局
（seed 2000/2001）**都是 `dropped=true` + `E_EVAL_TIMEOUT`**：

```
seed 2000: dropped=True error=E_EVAL_TIMEOUT decisions_llm=95 steps=111 stages=3
seed 2001: dropped=True error=E_EVAL_TIMEOUT decisions_llm=97 steps=112 stages=3
```

即 F20 刚实现的单局超时**如实生效**了，但它卡错了地方：

- `evals.seed_timeout_s` 是**墙钟**预算（`SandboxRunner` 的 deadline + `run_eval` 的硬看门狗都按它计时），
  而 `n_workers` 个局**共享同一个模型实例**（`max_inflight=1`），所以
  **单局墙钟 ≈ D × 每决策调用数 × t_d × n_workers**；
- 原值 1800 s 是按「实测单局 ≈546 s 的 3.3 倍」定的（§12），**没有把共享放大算进去**：
  96 决策点 × 1.4 调用/决策点 × 6.5 s × 2 worker ≈ **1750 s**，正好压在 1800 s 上；
- 于是 n=40 的每一局都会被判超时 → `n_dropped=40`、`low_confidence=true`，整批测量作废
  （而且这是**静默**的：报告只会显示 `n_dropped=40`，不会说「你的超时太紧」）。

**修复**：`evals.seed_timeout_s` 由 1800 s 调到 **5400 s**（`configs/default.yaml` +
`gamer_rsi/infra/config.py` + `EvalSpec` 默认值），并在配置里写下推导：
「300 决策点 × 1.5 调用 × 12 s(p95) × 2 worker ≈ 10800 s，取 1/2 余量 = 5400 s」。

**给 M2 的建议（本条只做了配置修正，没有改语义）**：墙钟预算与并发度耦合是个设计味道。
M2 更稳的做法是改成**计算量预算**（例如 `episodes.max_llm_calls` 或按 `t_d` 折算的
「等效推理秒数」），或者让 `run_baseline` 把 `timeout_s` 乘以在飞 worker 数——
这样「预算」的含义不会随 `n_workers` 漂移。
