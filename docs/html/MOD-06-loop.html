MOD-06 · loop

闭环编排器（Loop Orchestrator）

DiceRatchet L2 进化层的"节拍器"：它自己不产策略、不训练模型、不判改进好坏，只让 play → evaluate → reflect → evolve 这条闭环在一局、K 局、一代三个时间尺度上正确、可复现、可中断、可恢复地转起来。

版本 v1.2 状态：草案（待评审） 所属里程碑：M2 代码路径：dice_ratchet/loop/{runner.py, reflect.py, generation.py} 产物路径：runs/<run_id>/
背景与目标
让进化闭环在三个时间尺度上稳态运行：单局可跑通且逐字节可复现、局末必反思、每 K 局（默认 30）一次演化周期，run 级状态可续跑，失败不丢进度。
核心职责
单局决策循环编排、局末反思编排、演化周期调度（触发/幂等/计数）、run 状态机与 --resume 断点续跑、计分幂等去重、失败恢复矩阵、成本闸门、并发纪律。
服务对象
人类研究者（CLI 冒烟/跑代/续跑/HITL）、MOD-07 evolve（周期边界被调）、MOD-08 evals（读轨迹与计分台账）、回归测试、未来 MOD-10 distill。
关键成功度量
loop run --generations 3 --k 30 无人工干预跑通 ≥1 轮演化；Ctrl-C 后 --resume 接着跑完；scoreboard 中每个 episode_key 只计一次分。

1背景与目标

MOD-06 是 L2 进化层里的编排器。它不产生策略、不训练模型、不判定改进好坏——这些分别属于 MOD-04/03/07。它的价值在于让闭环可靠地转起来：在一局、K 局、一代三个时间尺度上保证正确、可复现、可中断、可恢复。

  1. 单局可跑通：EpisodeRunner 用固定 seed 驱动完整 episode，产出逐字节可复现的 JSONL 轨迹。
  2. 局末必反思：每局结束（win/lose/truncated）触发一次反思，结构化后写入 MOD-05；反思失败只降级、不阻塞主循环。
  3. 每 K 局一次演化周期：默认 K=30，触发 MOD-07；周期边界幂等，中断重入不重复触发。
  4. run 级状态可续跑：runs/<run_id>/state.json 记录 generation、已完成 seeds、待做队列、HITL 挂起标记；--resume 后不重复计分。
  5. 失败不丢进度：模型超时 / 环境异常 / 磁盘失败 / Ctrl-C 各有明确行为与 E_* 错误码。
成功定义（M2 验收）：loop run --generations 3 --k 30（或小 K 冒烟）无人工干预跑通 ≥1 轮演化；中途 Ctrl-C 后 --resume 接着跑完，且 metrics/scoreboard.json 中每个 episode_key 只出现一次计分记录。

2范围

记住一句话：MOD-06 只编排，不实现。它调用别人的能力，自己不写规则、不投影观测、不加载模型、不组 prompt、不存记忆。

✓ 负责（范围内）
  • 单局决策循环：observe → policy.play_decision → 逐行落盘 → 终止判定（步数/决策上限读 Spec §8.6 的 episode.*）
  • 局末反思编排（MOD-03/04 + harness/prompts/reflection.md，结构化后写 MOD-05，失败降级）
  • 演化周期调度：每 K 局触发 MOD-07、generation 计数器、读取 harness/version.json、周期边界幂等
  • run 级状态机、产物目录布局、--resume 断点续跑、计分幂等去重
  • 失败恢复矩阵与 E_* 错误码映射（前缀取自 Spec §8.3）
  • HITL 挂起/恢复的跨进程状态设计（配合 evolve approve|rollback）
  • 成本控制：按 Spec §8.6 统一计算每代局数 E_gen、预算耗尽行为
  • 并发：评估局局级并发 + 共享推理队列；训练局串行 + 共享记忆写入保护
  • 结构化事件与指标埋点
✗ 不负责（范围外）
  • 判定候选改进是否被接受（MOD-07）
  • 计算 held-out 指标（MOD-08）
  • harness 文件的具体 diff（MOD-07）
  • 实现游戏规则（MOD-01）、观测投影（MOD-02）
  • 加载模型（MOD-03）、组装 prompt 正文（MOD-04）
  • 实现记忆存储（MOD-05）
  • 定义 seed 切分协议（MOD-08）与 seed 注册表（MOD-09）——只读取已切分好的 seed 清单并消费
  • 自建日志格式与 run_id 生成（MOD-09）
  • 写 harness 文件、做 git commit（MOD-07/09）

4功能需求

共 16 条 FR，编号 FR-06-x，每条可测试。新人优先记住 FR-06-1/2（单局怎么跑）、FR-06-5/6（周期怎么触发且不重复）、FR-06-9/10（断了怎么续、分怎么不重）。

FR-06-1 单局时序

run_episode() 严格按 policy.reset(ctx) → env.reset(seed, episode_config) → 循环（policy.play_decision → 逐行落盘 → 终止判定）执行。终止条件只看 last.terminated or last.truncated；步数上限、决策上限和 policy_failure 都由 MOD-02 统一判定并以 truncated 返回（Spec B-15）——本模块不再维护 illegal_streak 或 max_steps。截断局 outcome="lose"，另记 truncation_reason，计入样本（Spec §8.6）。

FR-06-2 每步必落盘

每个 StepRecord（含 reject 行）立即追加到 episodes/<split>/<episode_key>.jsonl 并 flush，字段按 Spec v1.3 §4.5（MOD-09 schema 校验）。LLM 字段只挂在决策内第一个执行的动作行上。局末追加 episode_end 行。崩溃时最多丢当前决策。

FR-06-3 局末反思与用量回写

训练局结束（含截断）后两步走：先调 record_usage(episode_key, memory_ids, outcome, adopted_ids=…, tick=…) 回写本局所有决策的记忆使用情况（Spec §4.7）；若 reflect_enabled，由 loop.reflect.reflect 渲染 harness/prompts/reflection.md → MOD-03 generate_json() → 经 MOD-05 的 ReflectionEntry schema → add_reflection(entry, provenance)。EpisodeSummary 是确定性摘要（结局、关数、心数、战斗数、非法/fallback 次数 + 最近 reflect_context_window 局同类摘要），由本模块从轨迹生成，不经 LLM。评估局不反思、不回写（INV-5）。

FR-06-3a 逻辑时钟

tick = 已完成的训练局数，每局结束 +1，写入 state.json；它是 MOD-05 淘汰、TTL 与时新度的唯一时间源（Spec §8.1）。

FR-06-4 反思降级

反思任一步失败（超时 / JSON 非法 / schema 不符 / MOD-05 写失败）→ 事件 reflect 记 status="skipped"，reflections/<seed>.json 写 {"skipped": true, "reason": "<E_*>"}，主循环继续。反思失败绝不判该局失败、绝不阻塞 run。

FR-06-5 周期触发

每完成 K 局训练局触发一次演化周期，K = loop.k（默认 30）；条件为 len(completed_train_seeds) % K == 0 且 generation < loop.max_generations 且 phase == "playing"。

FR-06-6 周期幂等

同一 cycle_index 至多触发一次：先原子落盘 phase="evolving" + evolving_cycle=cycle_index，再调 MOD-07；返回后写 last_completed_cycle=cycle_index 并回 phase="playing"。若进程在 evolving 阶段被杀，--resume 不重跑 MOD-07，而是检查其产物（generations/gen-XXX/report.json / decision.json）存在性：存在则标该 cycle 完成，否则重置 phase="playing" 后重新触发。

FR-06-7 generation 与 harness_version

state.generation 单调不减，仅在 MOD-07 返回「本代已裁决」（接受或拒绝均算）后 +1；harness_version 每局开始时从 harness/version.json 重读（不跨代缓存），故 HITL 挂起期间人工切换 harness 立即生效。

FR-06-8 run 状态机

state.json 至少含 run_id / phase / generation / harness_version / k / completed_train_seeds / pending_queue / hitl_pending / counters / budget / updated_at（§7.1）；phase ∈ {pending, playing, reflecting, evolving, hitl_wait, done, failed}。

FR-06-9 断点续跑

loop run --run-id <id> --resume 读 state.json（config_hash 不含 harness，所以演化过的 run 也能续跑，Spec B-19），跳过 completed_train_seeds，从 pending_queue 头部继续，不重复计分（§7.3 幂等键）。

FR-06-10 计分幂等

计分只发生在 episode 正常收尾；写入前检查 metrics/scoreboard.json 是否已有该 episode_key，追加后 fsync。同 seed 因 --force-rerun 重跑时，旧记录标 superseded_by 而非删除。

FR-06-11 HITL 挂起

loop.hitl=true 时，MOD-07 产出候选与决策记录后不直接生效；MOD-06 写 state.hitl_pending={"cycle","generation","candidate_dir","report"}、置 phase="hitl_wait"、退出码 0（正常挂起非错误）。人工执行 evolve approve|rollback --generation g（MOD-07 命令，MOD-06 只消费结果状态）后，loop run --run-id <id> --resume 读 harness/version.json 与 hitl_pending，清空标记并继续。

FR-06-12 评估执行器

MOD-08 evaluate_arm() 通过注入的 EpisodeRunner.run_episode(split="heldout", arm=...) 执行评估局。本模块只负责执行与落盘，不做任何聚合指标（聚合归 MOD-08）。v1.0 的 run_evaluation_batch() 已并入 MOD-08 门面。

FR-06-13 成本闸门（Spec v1.3 §8.6）

  • 每代启动前按 E_gen = K + (H + S) + C·(S + H) 计算本代局数：训练 K、parent 的 heldout H 与冒烟 S、C 个候选各自的冒烟与 heldout。默认 30 + 45 + 2×45 = 165。
  • E_gen > loop.max_episodes_per_generation（默认 170）时拒绝启动该代，记 loop.budget_exhausted，退出码 1，并提示下调 C 或 S。这是全系统唯一的成本上限，MOD-07 不另设。
  • 每代开始写一条 loop.cycle_start{e_gen, est_hours} 事件，其中 est_hours = E_gen × D × t_d，t_d 取 MOD-03 实测 p50。

FR-06-13a gen-000 基线

run 启动时（generation=0），先对 harness v0 在 H1 上调 MOD-08 evaluate_arm 与 evaluate_generation，生成 generations/gen-000/report.json（decision="baseline"），后续各代与它对比。

FR-06-14 并发纪律

  • 训练局串行（train_concurrency 固定 1）；写共享记忆须持 runs/<run_id>/locks/memory.lock 文件锁。
  • 评估局局级并发：eval_concurrency 默认 2，同一进程内用 asyncio/线程，共享同一个 BackendManager 推理队列（Spec P-10 / §8.6）。评估局使用冻结的 harness 快照与 memory.frozen(v) 只读视图，禁止写记忆库。
  • v1.0 的进程池方案每个 worker 各载一份权重，24 GB 内存放不下，已废弃。

FR-06-15 信号处理

捕获 SIGINT/SIGTERM：完成当前 step 落盘 → 写 state.json（附 interrupted_at）→ flush → 退出码 130；第二次信号立即 os._exit(130)。

5非功能需求

NFR 围绕四个词：确定性、可复现、可观测、崩溃安全。这是编排器最容易被忽视、却最不能让步的部分。

  • NFR-06-1确定性：同一 run_id + 同 seed 清单 + 同 harness_version + mode=eval（温度 0）时，评估局与并发度无关，且 obs_digest/action/reward 序列逐字节一致；所有随机来自 dice_ratchet.infra.rng_for(seed, namespace)，禁用 random/time 相关随机（MOD-09 guards.py CI 扫描）。
  • NFR-06-2可复现：state.json 能独立重建「下一步做什么」，不依赖内存态；runs/<run_id>/config.json 固化合并后配置（含 config_hash）。
  • NFR-06-3性能：编排层单步开销（不含推理与环境 step）≤ 5 ms（M5 本机）；每步 ≤ 1 次 append+flush；代际目录用增量读，不整目录 glob。
  • NFR-06-4可观测：事件统一经 MOD-09 emit 写入 events.jsonl，名称为 loop.{episode_start,episode_end,cycle_start,reflect,budget_exhausted,interrupted,resume}（Spec §8.2）。轨迹行不是事件。v1.0 的 metrics/loop_trace.jsonl 已废弃。
  • NFR-06-5崩溃安全：state.json 与 scoreboard.json 一律「临时文件 + os.replace」原子替换；episodes/*.jsonl 追加+flush；任意时刻 SIGKILL 最多丢当前步，状态文件不自相矛盾。
  • NFR-06-6可测性：EpisodeRunner 依赖可注入（env/policy/memory/clock/log_writer），全部可用 tests/fakes.py 假实现替换；loop smoke --no-reflect 不触网不调模型，< 2 s 跑完 3 局。
  • NFR-06-7内存：常驻内存不随局数增长——轨迹流式写盘不累积 list[StepResult]，反思上下文只保留最近 reflect_context_window 局摘要。

7数据模型与存储

7.1 run 产物目录（扩展 Spec §5）

一个 run 的所有证据都落在 runs/<run_id>/ 下。记住所有权：state.json 是本模块权威，config.json 与 events.jsonl 由 MOD-09 写，generations/ 由 MOD-07 写、本模块只读。

runs/<run_id>/
  config.json             # 合并后配置 + config_hash（MOD-09 写，本模块只读）
  state.json              # run 级状态机（本模块权威，§6 schema）
  queue.jsonl             # 待做队列追加式事件日志（add/done/skip），供恢复与审计
  events.jsonl            # 结构化事件（MOD-09 emit）
  episodes/<split>/<episode_key>.jsonl   # 每步一行（Spec v1.3 §4.5 字段，本模块写）
  reflections/<seed>.json # 每局一份反思或 skipped 标注
  generations/gen-<NNN>/  # MOD-07 写的候选与报告；本模块只读、只检查存在性
  metrics/scoreboard.json # 计分台账（幂等键 episode_key）
  locks/memory.lock       # 训练局共享记忆写入文件锁
  audit/                  # MOD-02/09 审计产物

7.2 状态机转移

pending → playing → (reflecting → playing)* → evolving → (hitl_wait → playing | playing) → … → done

异常边：任意 phase → failed（不可恢复，如 E_IO_RUN_STATE）；playing → interrupted（临时态，恢复回 playing）。

7.3 幂等键

  • 计分幂等：episode_key = f"e-{seed:06d}-g{generation:03d}-{arm}"（Spec v1.3 §4.5 / B-16，取代 P-13 的旧格式）。同一 seed 在不同代、不同臂下各计一条记录，同代同臂内重复执行只保留一条。
  • 周期幂等：cycle_index = len(completed_train_seeds) // k，以 last_completed_cycle + evolving_cycle + MOD-07 产物存在性三重校验。
  • 反思幂等：reflections/<seed>.json 已 status=="ok" 则跳过；skipped 需 --retry-reflections 显式重试。
  • 已裁决（Spec v1.4 B-36，与 P-14 一致）：训练/评估 seed 必须经 MOD-08 evals.seeds.take 取用，MOD-06 不得自行按 seed % 2 之类规则切分；仅校验传入 seed 的 split 标签与 MOD-08 注册表一致，不一致立即抛 E_EVAL_SPLIT_VIOLATION（守 INV-5）。

8关键流程

单局决策时序（FR-06-1/2）

每个 episode 都严格走这六步，循环体里"落盘"必须先于"终止判定"，保证崩溃时最多丢当前决策。

1 · 构造 EpisodeContext
run / episode / seed / split / mode / tick / memory（评估局用 frozen 只读视图）
→
2 · policy.reset(ctx)
→
3 · env.reset(seed, episode_config)
→
4 · emit loop.episode_start
→
5 · 循环：play_decision → 逐行落盘（append+flush）
LLM 字段只挂决策内第一个执行动作行
→
6 · 终止判定
仅看 terminated or truncated（B-15，MOD-02 判）→ 写 episode_end → record_usage → emit loop.episode_end

局 / 周期双层调度（FR-06-5/6/9）

外层是"一局一局跑"，跑完 K 局尝试进入演化周期；周期触发前先原子落盘 phase="evolving"，这是幂等的关键。

1 · 加载/初始化 state
resume 读 state.json，否则 init_state；过滤已完成 seed
→
2 · 每局开头重读 harness_version
不跨代缓存（FR-06-7）
→
3 · run_episode(train) + score_once 幂等计分
→
4 · completed +1，tick +1
phase=reflecting，写反思或 skipped
→
5 · 周期边界？
cycle > prev 且 generation < max_generations
→
6 · 成本闸门
E_gen > cap → budget_exhausted + failed（退出码 1）
→
7 · 先落盘 evolving，再调 evolve_fn
返回后 last_completed_cycle=cycle，generation += 1
→
8 · HITL？
hitl=true 且 pending_human → phase=hitl_wait，退出码 0；否则回 playing

# EpisodeRunner.run_episode —— 决策时序（FR-06-1/2）
def run_episode(self, seed, *, split, arm, episode_config, harness_version):
    key = f"e-{seed:06d}-g{self.run_ctx.state.generation:03d}-{arm}"
    ctx = EpisodeContext(run=self.run_ctx.run_id, episode=key, seed=seed, split=split,
                         mode="train" if split == "train" else "eval", tick=self.run_ctx.state.tick,
                         memory=self.memory if split == "train" else self.memory.frozen(self.run_ctx.memory_version))
    self.policy.reset(ctx)
    obs = self.env.reset(seed, episode_config=episode_config)
    emit("loop.episode_start", episode_key=key, seed=seed, split=split, arm=arm, harness_version=harness_version)
    used, adopted, cum = [], [], 0.0
    with self.writer.episode(split, key) as w:        # episodes/<split>/<key>.jsonl，append + flush
        while True:
            d = self.policy.play_decision(self.env, obs, ctx=ctx)   # MOD-04：计划 + 重试 + fallback
            for i, rec in enumerate(d.steps):
                cum += rec.result.reward
                w.write_step(rec, cum_reward=cum, llm=d.llm if i == first_llm_step(d) else None,
                             prompt_hash=d.prompt_hash, memory_ids=d.memory_ids)   # Spec §4.5（FR-06-2）
            used += d.memory_ids; adopted += d.adopted_memory_ids
            obs = d.last.observation
            if d.last.terminated or d.last.truncated: break    # 截断由 MOD-02 统一判定（B-15）
        w.write_end(native_of(d.last.info))                    # episode_end 行
    rec = RecordedEpisode(episode_key=key, outcome=d.last.info["outcome"] or "lose", ...)
    if split == "train":
        self.memory.record_usage(key, dedup(used), rec.outcome, adopted_ids=dedup(adopted), tick=ctx.tick)
    emit("loop.episode_end", **asdict(rec))
    return rec

# LoopOrchestrator.run —— 局/周期双层调度（FR-06-5/6/9）
def run(self, seeds=None, *, resume=False):
    st = load_state(self.run_ctx) if resume else init_state(self.run_ctx, seeds)
    st.pending_queue = [s for s in (seeds or st.pending_queue)
                        if s not in set(st.completed_train_seeds)]   # 不重复做（FR-06-9）
    save_state(st)                                                   # 原子替换
    while st.pending_queue:
        st.phase, st.harness_version = "playing", read_harness_version()  # 每局重读（FR-06-7）
        seed = st.pending_queue[0]
        rec = self.runner.run_episode(seed, split="train", arm="train", harness_version=st.harness_version,
                                      episode_config=self.run_ctx.episode_config)
        score_once(st, rec)                       # 幂等：episode_key 已存在则跳过（FR-06-10）
        st.completed_train_seeds.append(seed); st.pending_queue.pop(0)
        st.counters.episodes_total += 1
        st.counters.episodes_truncated += (rec.truncation_reason is not None)
        st.tick += 1                              # 逻辑时钟（FR-06-3a）
        st.phase = "reflecting"; save_state(st)
        r = reflect(summarize_episode(rec, window=recent(st)), client=self.client,
                    template=harness_path("prompts/reflection.md"))            # FR-06-3
        write_reflection_or_skip(rec, r)          # None → {"skipped":true,...}（FR-06-4）
        st.phase = "playing"; save_state(st)
        cycle = len(st.completed_train_seeds) // st.k
        prev = -1 if st.last_completed_cycle is None else st.last_completed_cycle
        if cycle > prev and st.generation < self.config.max_generations:   # 唯一触发条件（FR-06-5 以此为准）
            if episodes_per_generation(self.config) > self.config.max_episodes_per_generation:
                emit("loop.budget_exhausted"); st.phase = "failed"; save_state(st); return summarize(st)   # FR-06-13
            st.phase, st.evolving_cycle = "evolving", cycle
            save_state(st)                        # 先落盘再调 MOD-07（FR-06-6）
            out = self.evolve_fn(st, self.run_ctx)     # MOD-07：候选生成+held-out 裁判+裁决
            st.last_completed_cycle, st.evolving_cycle = cycle, None
            st.generation += 1                    # 接受或拒绝均 +1（FR-06-7）
            if self.config.hitl and out.pending_human:
                st.hitl_pending = {"cycle": cycle, "generation": st.generation,
                                   "candidate_dir": out.candidate_dir, "report": out.report}
                st.phase = "hitl_wait"; save_state(st); return summarize(st)   # 退出码 0
            st.phase = "playing"; save_state(st)
    st.phase = "done"; save_state(st); return summarize(st)

并发时序（FR-06-14）

评估一律经 MOD-08 evaluate_arm() 执行：局级并发 eval_concurrency（默认 2），所有局共享同一个 BackendManager 串行推理队列（P-10），每局有独立的 SandboxEnv 与 memory.frozen(v) 只读视图（v1.4 / Spec v2.2 B-46：这句原先只是意图——代码曾把同一个 SandboxEnv 交给 n_workers=2 的两局并发驱动，观测串局 ⇒ illegal_rate ≈0.285 / fallback_rate ≈0.29（缺陷 F30）；现已改为每局经 env_factory 新建、局末 close()，并有 tests/integration/test_loop_env_isolation.py 护栏）。评估局不写 scoreboard.json 主台账，只写 episodes/<split>/（Spec P-15 已采纳）。并发只能掩盖 env 与 IO 的开销，不能缩短推理瓶颈；耗时按 Spec §8.6 估算。

12验收标准（DoD）

对齐 Spec §9 质量门 G1–G6。所谓"交付完成"，就是下面每一项都能打勾。

  • G1 单测：dice_ratchet/loop/** 行覆盖率 ≥ 75%（编排层含 IO，阈值低于纯函数模块的 80%）；T-06-1…T-06-13 全绿。
  • G2 Golden：本模块不产出 golden 轨迹（归 MOD-01/02），但必须消费其 golden seed 集跑通且不修改既有 golden 文件。
  • G3 确定性：T-06-15 通过；loop/ 经 MOD-09 guards.py AST 扫描 0 处 random/time 依赖。
  • G4 泄漏审计：python -m dice_ratchet audit leak --run-id <run_id> 对本模块产出的 run 0 告警；state.json 与 reflections/*.json 中不得出现 held-out/test seed 值（按 MOD-08 seed 注册表白名单正则扫描）。
  • G5 Schema：§6 的 JSON Schema 落 dice_ratchet/loop/schemas/，round-trip 测试通过。
  • G6 可复现命令：§3 四条命令在干净 checkout 上可直接复制执行成功（含 --no-reflect 免模型路径）。
  • M2 验收（计划 §7 / Spec §7）：闭环自动运行 ≥1 轮演化并产出 diff 与决策记录；--resume 与 HITL 挂起/恢复各有一条端到端演示记录（README 附命令与日志片段）。
  • 计分正确性：任意中断/恢复组合下，scoreboard.json 的 episode_key 集合等于「实际完整跑完的 episode 集合」，无重复、无幻影。

16开放问题

这些是 PRD 明确尚未定案的问题。新成员若要改动相关设计，先确认这些问题的最新结论。

  1. K 的取值：计划 §5 给 K=30，但 M2 冒烟只有 K=3 才现实。是否引入 k_schedule（前 3 代为 5、之后 30）？需 MOD-08 给出统计功效依据后再定。
  2. 计分幂等键是否应含 config_hash：现为 e-<seed>-v<harness_version>。若同一 run_id 下改了 episode_config（如难度），是否需扩展键？倾向扩展，但会让历史数据对比复杂化。
  3. truncated 样本处置：当前计为样本但 outcome=None。是否应像降级局一样标 not_for_eval？待 MOD-08 定口径后回填 Spec §4.1。
  4. 单模型下的评估并行：24GB 未必能容两份 8B 权重 + KV cache。是否需 MOD-03 提供「单进程批量推理服务器」作为第二方案（本 PRD 仅保留 workers=1 顺序退化）。
  5. HITL 挂起期间 harness 被外部改动：--resume 只读 version.json，无法判断改动是否对应本次挂起的候选。是否要求 MOD-07 在 version.json 写 pending_cycle 供校验？
  6. state.json 是否保留历史快照：现只保留最新态 + queue.jsonl 事件流。若需重建任意时刻状态，可能要请 MOD-09 增加状态快照归档（与「轨迹保留 ≥ 全部代际」对齐）。
  7. skipped 反思的补偿：run 结束时是否统一补跑一次（批量、离线）？补跑会改变记忆内容进而影响后续局，破坏确定性，倾向不做，需确认。
