MOD-03 inference

系统里唯一的模型出口。它要同时满足五个约束：本地可离线、输出能被 JSON Schema 收敛、24 GB 内存不炸、评估时能被并发调用、以及“同 seed 同配置尽量可复现”。

L1 智能体 ✅ 已落地 MLX / llama.cpp / mock / DeepSeek API 三角色绑定

01一个出口，多个后端

上层（MOD-04/06/07/08）只知道 InferenceClient.generate_json()，不需要知道背后是 MLX、llama-server 还是 HTTP API。新增一个后端只需要实现 Backend 协议与 name/model_id 属性。

模型是配置，不是代码。同一套代码可以用“三角色全本地 8B”跑离线，也可以切到“三角色全 deepseek-flash”（实验臂 C1）。

02三级 JSON 修复：不让坏格式毁掉一整局

为什么不是“重试到成功”。修复重试必须带具体校验错误；无信息重试只会烧 token。全程墙钟上限保证一次坏调用不会卡死整代。

预算按调用方给，而不是全局抬高

历史上提案与决策共用一个全局 max_tokens=256，导致提案（约需 500 token）一律被截断、被误报成 schema 错误，闭环静默定格。现在由调用方显式给预算：

调用方预算温度 / seed
决策 PolicyAgentagent.policy.max_tokens=320训练 0.7–1.2；评估固定 0.0
局末反思256（sampling.max_tokens）评估温度 0.0，seed=0
harness 提案 proposer_PROPOSE_MAX_TOKENS=2048按配置；不受 256 全局值限制
诚实边界：API 后端不承诺“同 seed 逐字节复现”（同一请求字节多次返回不同响应）。所以 G3 的确定性承诺按层执行：本地臂硬校验；含 API 角色的臂只发 eval.nondeterministic 事件，不抛异常。

03内存与并发：先算预算，再提交推理

公式：required_gb = resident_gb_est + kv_gb_per_1k_tokens × (context_length/1000) × max_inflight + 1.0。超过 ram_budget_gb 就在 acquire 信号量之前抛 E_LLM_OOM——零提交，不产生半截请求。

常驻预算 20 GB

24 GB 机器留 4 GB 给 Python / 环境 / OS。8B Q4 实测常驻 4.61 GB。

并发可配

inference.max_inflight 默认 4；评估模式强制 1。局级并发靠 loop.eval_concurrency，而不是模型级批处理。

失败可降级

加载失败可退避后换 fallback_backend 重试一次；OOM、超时、schema 失败都以 E_LLM_* 暴露给上层决定。

前缀缓存只对本地有效

cache_prompt 只被 llama-server 消费；API 臂没有本地 prefill，缓存命中率也不可测。

04错误码：模型侧失败长什么样

错误码触发上层怎么处置
E_LLM_UNAVAILABLE未知 model_id / 权重缺失 / sha256 不符 / 角色无绑定退出码 3；不静默换模型
E_LLM_LOAD_FAILED后端加载失败退避后换 fallback 后端重试 1 次
E_LLM_OOM内存预算前置拒绝，或真实 OOM不提交推理；可降级到 fallback
E_LLM_TIMEOUT单次 / 全程墙钟超时该次调用失败；由 MOD-04 fallback
E_LLM_SCHEMA_INVALID三级修复耗尽决策改走启发式；不污染指标
E_LLM_CONTEXT_OVERFLOWprompt + max_tokens 超上下文reject 直接抛；truncate 截最早消息
E_LLM_NONDETERMINISTIC同一 request hash 的 API 响应变化绝不覆盖旧证据；发 llm.nondeterministic 事件
