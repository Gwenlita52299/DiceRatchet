MOD-02 env-sandbox

L0 与 L1 之间唯一合法的数据通道。它同时做三件互相独立的事：把隐藏信息裁掉（防泄漏）、把自编辑代码关进笼子（防越权）、把“有没有漏”变成可复算的审计结论（防未被发现的泄漏）。

L0 环境 ✅ 已落地 INV-1 / INV-2 / INV-3 / INV-4 规则集 1.1.0

01三道防线，各管一件事

三道防线不共享故障模式。投影错了，隔离仍然拦代码；隔离被绕过，审计仍能从产物里发现泄漏；蜜罐则保证“审计器本身没坏”。

02投影：白名单是唯一权威

project_state() 只输出 OBSERVATION_SCHEMA 里 enabled=True 的字段。它不直接读 GameState：输入是 MOD-01 observe(state, "full") 的白名单结果，再叠三个 agent 专属键（episodeId / decisionIndex / lastResult）与 stageCount。因此隐藏信息有两道彼此独立的防线。

规则行为为什么
未登记字段丢弃，只记 dropped_hidden 计数日志里记字段名本身就是反向泄漏
schemaVersion由投影层覆盖式注入源里的同名值不可信
字段增删 / 类型变更主版本 +1，并追加 OBSERVATION_CHANGELOG.mdCHANGELOG 末行版本 = 代码常量，CI 校验
两次投影canonical JSON 与 obs_digest 逐字节相同纯函数、无随机、无时间依赖
为什么“不记字段名”也是规则。如果日志写“发现隐藏字段 enemyGroupId 被丢弃”，读日志的 agent 就免费获得了隐藏信息的存在与名字。所以统计只保留数量。

03一步动作的完整检查顺序

先测后提交。不变式校验针对 reduce 产出的新状态；一旦违反，这一步被整体丢弃，环境保持在上一步的合法状态。

失败之后不“重试到过”也不静默跳过，而是按调用方既有的恢复矩阵处置：训练路径记 audit/env_error_<seed>.json 并跳过该 seed，同类累计 ≥3 次中止 run；MOD-08 批量测量记 dropped（计 n、按 lose 计、错误码入档）。

04审计：6 类泄漏，3 个扫描面

种子类

seed_leak——train seed 的字面量出现在 prompt / memory / log。数字串扫描带字符边界，浮点小数部分不算。

未来信息

future_room_leak / shop_content_leak——逐局作用域：只比较这一局真正可能看到的未来房间与商店。

字段类

full_state_field_leak / hidden_field_name_leak——全量状态字段名或隐藏字段名出现在文本里。

蜜罐

canary_leak——注入的 canary / 假字段一旦出现，100% 判 critical。自测 12/12 命中才算审计器可用。

退出码含义轴
0无 finding泄漏结论轴
1仅 medium（字段名类）
2含 critical（种子 / 未来 / 商店 / canary）
4审计器自身失效：蜜罐自测 <100%，或规则集钉扎不符（E_ENV_AUDIT_RULESET）守卫轴（优先于结论轴）
审计不是“每代自动跑”。触发方式是显式 CLI：python -m dice_ratchet audit leak --run-id <id>。配置里只有 sandbox.audit.ruleset_pin 一个键，它必须等于代码常量 RULESET_VERSION="1.1.0"；不符就 fail-closed，避免“用旧规则宣布 clean”。

05配置面：从 15 个键砍到 2 个

2026-10-14 的逐键核查发现：env.sandbox.* 原有 15 个键，只有 2 个真的有消费者。其余 13 个不是“忘了接线”，而是“本就不该是可配项”。

保留的键默认消费者 / 语义
env.sandbox.policy_failure_streak3连续 reject(final=True) 达到即判 policy_failure
env.sandbox.audit.ruleset_pin1.1.0规则集版本钉扎；必须是代码常量的镜像

删掉的 13 个包括：guard.enforce（warn 档会削弱 INV-4）、scan_roots（扫描面是分层结构，不是参数）、honeypot.enabled（给不变式留静默关闭点）、projection.schema_version（必须不可被配置伪造）、exec.*（沙箱上限正是 INV-4 要防的东西）等。

一次真实教训：2026-10-14 之前 future_room_leak 是跨局作用域，同一批工件复跑得到 5,852 条 critical findings；改成逐局后是 clean / 0 findings。这类“审计器误报”比漏报更难被发现，因为它看起来很有产出。
设计上的取舍：审计按 content_hash 反查真实配表。如果一个都对不上，就判 critical 并降级 future_room / shop 两类规则集——宁可承认“这次没查全”，也不拿默认配表凑数。
