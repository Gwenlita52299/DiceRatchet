MOD-02 · env-sandbox

环境沙箱：投影 · 隔离 · 审计 · 蜜罐

它是 L0 游戏引擎与 L1+ agent 之间唯一合法的数据通道——把「agent 只能看到它该看到的」这条项目最硬的纪律落到代码层，用三条独立防线守住：投影裁剪防泄漏、代码/进程隔离防越权、审计与蜜罐防「泄漏没被发现」。

版本 v1.2.2 状态：草案（待复核） 里程碑：M0（SandboxEnv + 投影 + 审计器 + 蜜罐自测全部交付） 2026-10-03 追加 §18 实现落地记录

⚠️ 本页为手工镜像，不随 PRD 自动生成；本次按 2026-10-14 现状增量修订。

背景与目标

计划 §3 与「米哈游小丑牌透视预读」教训定下纪律：agent 只能看到它该看的。MOD-02 是这条纪律在代码层的唯一执行者，提供三条独立防线：投影裁剪（防泄漏）、代码/进程隔离（防越权）、审计与蜜罐（防未被发现的泄漏）。

核心职责

五个 stdlib 文件撑起整条防线：projection.py（字段级白名单投影）、api.py（SandboxEnv 唯一入口）、guard.py（import 门禁 + 受限执行）、audit.py（泄漏审计）、honeypot.py（蜜罐探针）。

服务对象

MOD-04 policy 取 obs 组装 prompt；MOD-06 loop 驱动单局；MOD-07 evolve 让候选工具先过门禁再入库；MOD-08 evals 把审计结果纳入评估；MOD-09 infra 暴露 CLI 与 CI 门禁；评测复核者事后回答「它有没有看到不该看的」。

关键成功度量

G1 五模块单测覆盖 ≥80%；G3 同 seed 双跑 obs_digest 逐字节相同；G4 蜜罐 12/12 用例被抓到、注入 canary 100% 触发 P0；运行期硬约束：honeypot_caught_rate 恒为 1.0、canary_leak==0。

1背景与目标

MOD-02 是 L0 与 L1 之间唯一合法数据通道。M0 给出五条可检验的目标：

  1. 交给 L1+ 的环境数据只可能来自 dice_ratchet/sandbox/projection.py::project_state()——未在 OBSERVATION_SCHEMA 登记的字段无法出现在 Observation（INV-2）。
  2. agent 侧 import dice_ratchet.env.* 在 CI 与运行期两级被拒（INV-1）。
  3. 自编辑 harness 代码只能在受限执行器内运行：无网络、无文件写、无 subprocess、无 env 访问（INV-4）。
  4. audit leak 能从轨迹与 prompt 重建「agent 可见信息集合」，并对 6 类泄漏做结构化判定（INV-2/3/5）。
  5. 蜜罐 canary 与假字段一旦泄漏，100% 被抓到（G4）。

4功能需求

共 24 条 FR（FR-02-1 ~ FR-02-24），每条都可独立测试。按四条防线分组讲解：

投影防线：唯一权威登记表

  • FR-02-1project_state() 是纯函数：不读全局、不调用 random/time/os.environ；同输入两次调用 canonical JSON 逐字节相同。
  • FR-02-2只输出 OBSERVATION_SCHEMA 中 enabled=True 的字段；源 state 存在但未登记的字段一律丢弃，只记计数、不记名称。
  • FR-02-3输出不得包含 Spec v1.3 §4.2「严禁出现」的任何值：seed、RNG 流状态、未来骰面（抽骰堆顺序）、未揭示的地图行、商店未展示商品、敌人未公开状态、GameState 全量；以逐字段哨兵替换测试验证不可反向推回。
  • FR-02-3a投影源是 MOD-01 observe(state, "full")（GAME obs-1.0.0，已经是游戏侧白名单），本模块在其上再做键子集 + 3 个 agent 专属键（episodeId/decisionIndex/lastResult）+ stageCount，字段名保留 camelCase。不直接读 GameState，因此隐藏信息有两道防线。
  • FR-02-3brender_compact(obs) -> str：确定性的紧凑文本渲染，供 MOD-04 填入 {{observation}}。地图只展开下一行的可达节点，手骰、槽、敌人各占一行。p95 ≤ 1,500 token（8B 分词器）。
  • FR-02-4OBSERVATION_SCHEMA 不可变；字段增删/类型变更必须 OBSERVATION_SCHEMA_VERSION 主版本 +1，并在 docs/prd/OBSERVATION_CHANGELOG.md 追加「版本/日期/字段/digest 影响/PR 号」。
  • FR-02-5CI 校验 CHANGELOG 末行版本 == OBSERVATION_SCHEMA_VERSION，不一致则 E_ENV_PROJECTION_VERSION。运行时不读文档目录（v1.0 在 import 时读 docs/，打包后会失效）。
  • FR-02-6schema_version 由投影层强制注入，同名源字段被覆盖（防伪造）。
  • FR-02-24mode="strict" 记 dropped_hidden 计数并告警；mode="assert" 命中隐藏字段即抛 E_ENV_SCHEMA（供 golden/CI）。

门面防线：唯一入口，FullState 绝不外泄

  • FR-02-7SandboxEnv 私有持有 self._engine，无任何返回 FullState 的公开成员；step() 内先算 state_hash/obs_digest 再丢弃 full_state 引用。
  • FR-02-8非法动作由 MOD-01 判定；step() 返回 reward=-0.05, info={"illegal":True,...} 且不抛异常、观测不变（lastResult 更新）。
  • FR-02-8areject(*, stage, reason, raw, final)（Spec §4.1/§4.3，P-02 结案）：L1/L2 校验失败时由 MOD-04 调用，不改状态，illegal_count += 1，shaped -0.05，写一行 illegal=true 的轨迹。
  • FR-02-8b唯一判负方（B-15）：连续 3 次 reject(final=True)（中间没有成功的决策）→ truncated=True, info.truncation_reason="policy_failure"，主指标计为 lose。另外 episode.max_env_steps/max_decisions 超限 → truncation_reason="step_limit"/"decision_limit"。MOD-04/06 不另行判负。
  • FR-02-8clegal_actions() = MOD-01 legal_actions 去掉 abandon_run，顺序保持不变；hints() 转发 play_hints 供启发式使用（只含公开信息）。

隔离防线：import 门禁 + 受限执行

  • FR-02-9check_imports() 扫描 L1–L3（agent/memory/loop/evolve/evals/inference）中任何 import dice_ratchet.env... / from dice_ratchet.env import ...，命中即 E_ENV_IMPORT_DENIED。
  • FR-02-10install_agent_import_hook() 安装不可卸载的 MetaPathFinder，按调用方模块路径判定：调用栈中发起 import 的帧属于 dice_ratchet.{agent,memory,loop,evolve,evals,inference} 时拒绝 dice_ratchet.env.* 并抛 E_ENV_IMPORT_DENIED；dice_ratchet.sandbox 自身的导入放行。另外，SandboxEnv 模块在安装 hook 之前预先 import env。
  • FR-02-11子进程边界 run_agent_tick()：[sys.executable, "-I", "-S", "-c", shim]，清空 PYTHONPATH、cwd 只读、stdin/stdout 仅 JSON 协议、超时即 kill；供不配合 hook 的第三方代码。
  • FR-02-12analyze_code() 采用节点黑名单 + 调用白名单：禁止 BLOCKED_NODES（Import/ImportFrom 仅放行 tool_import_allowlist 内模块）、BLOCKED_CALLS、BLOCKED_MODULES、ATTR_DENY（任何 __*__ 属性）；运算符、比较、布尔、切片、推导式等表达式节点一律允许（v1.0 的节点白名单漏掉了 Add/Eq/And/USub…，任何写了 a + b 的合法工具都会被拒）。返回全部违规的行号与错误码。
  • FR-02-13gate(artifact_dir) 对 harness/tools/*.py 逐个 analyze_code，任一失败整批拒绝（fail-closed），写 runs/<run_id>/audit/harness-gate.json，旧 harness 保持可用。
  • FR-02-14常驻子进程 worker（Spec B-20）：load_harness_tools(harness_dir) -> ToolWorker 启动 [sys.executable, "-I", "-S", worker.py]。RLIMIT_AS/RLIMIT_CPU/RLIMIT_NOFILE 只设在子进程；工具代码 exec 进 guarded_globals()；父子按行传 JSON，请求为 {tool, obs, candidates, memory}；每次调用有墙钟 timeout_s，超时就 SIGKILL 并重启 worker，抛 E_ENV_TIMEOUT。主进程持有模型，绝不设置 rlimit（v1.0 在进程内设 RLIMIT_AS=256MB，会直接杀掉持有 5～19 GB 权重的主进程）。
  • FR-02-15受限执行期监测逃逸：代码触碰 _HONEYPOT_* 命名或 honeypot ledger 即产生 E_ENV_ESCAPE P0 事件（sentinel 属性触发）。

审计与蜜罐防线：让泄漏无处遁形

  • FR-02-16rebuild_visible_set() 从 episodes JSONL + prompt/memory 文本重建 VisibleSet：obs_paths、obs_digests、memory_texts、harness_version、seeds_seen。
  • FR-02-17扫描 6 类：seed_leak、future_room_leak、shop_content_leak、full_state_field_leak、hidden_field_name_leak、canary_leak，每类输出 finding 明细。
  • FR-02-18扫描面覆盖 prompt（LLM 真实入参）、memory（记忆写入）、log（JSONL 全字段）；任一出口命中即 P0。future_room_leak／隐藏 token 的判定是逐局作用域：某局只用本局的 hidden − shown；memory/ 全局库与 events.jsonl 用 unscoped（= 任何一局都从未合法展示过）。
  • FR-02-19run_audit() 输出严格符合 audit/report.schema.json；退出码 0 无 finding / 1 仅 medium / 2 含 critical；evidence 仅保留命中 token 前后各 evidence_chars（默认 12）字符，报告权限 0600，避免报告自身成为泄漏载体。
  • FR-02-20honeypot.inject() 的注入点改为 GAME 状态中真实存在的隐藏位置：未揭示地图行节点 preview.enemyNames 中嵌入 HONEYPOT_CANARY；state.node.shop 未展示库存加 _np_secret_price；抽骰堆 player.drawPile 末尾的虚构骰 _np_future_die；enemies[]._np_hidden_status。注入只作用于投影前 state 的副本，不影响 stateDigest 对拍。
  • FR-02-21canary 与 3 个假字段名不得出现在 OBSERVATION_SCHEMA 任何 source_path 中；注册表导入时断言，违反抛 E_ENV_HONEYPOT。
  • FR-02-22honeypot.scan(text) 用字节级 .find()（非正则）匹配每个 canary/假字段，命中产 HoneypotHit + audit_honeypot_triggered 事件。
  • FR-02-23honeypot.self_test() 生成 12 条用例（prompt/memory/log × canary/假字段），命中率必须 100%；audit leak 前强制执行，低于 100% 直接判 critical。

5非功能需求

  • NFR-02-1 确定性project_state/obs_digest 无随机、无时间依赖；canonical JSON 统一用 MOD-01 stable_stringify（sort_keys=True, ensure_ascii=True, separators=(",",":")，与 JS 一致，Spec P-21 结案）；PYTHONHASHSEED=0 下同 seed 重跑 obs_digest/state_hash 序列逐字节相同（G3）。
  • NFR-02-2 性能投影 + 紧凑渲染 p95 ≤ 2 ms/步（GAME 观测约 12k 字符，v1.0 的 200 µs 是按旧观测估的）；审计 ≤2 s/1000 步；工具 worker 单次调用往返 ≤ 20 ms（常驻进程，不含首次启动）；worker 冷启动 ≤ 150 ms。
  • NFR-02-3 可复现报告含 ruleset_version/run_id/config_hash；同 run 两次审计除 generated_at 外逐字节相同。
  • NFR-02-4 可观测+fail-closed拒绝/超时/触发全部产结构化事件，不自建日志格式；E_ENV_* 在 infra/logging.py 集中登记；隔离与门禁的内部错误默认拒绝（拒绝执行/判 critical），绝不静默放行。
  • NFR-02-5 可测性5 个文件仅用 stdlib；projection/audit/honeypot 为纯函数模块，单测覆盖率 ≥80%（G1）。

10错误处理与降级

总原则：隔离类错误 fail-closed（拒绝执行）；能力类错误 fail-soft（退回 fallback，该局标注降级且不计入评估样本，遵循 Spec §8.5）。

错误码触发处理/降级
E_ENV_PROJECTION_MISSING非 optional 字段源缺失终止该局，不返回部分观测
E_ENV_PROJECTION_VERSIONCHANGELOG 末行 ≠ 注册表版本CI 失败（运行时不读文档）
E_ENV_SCHEMAmode="assert" 命中隐藏字段、类型不符、观测校验失败抛错；golden/CI 直接红
E_ENV_IMPORT_DENIEDagent 侧 import dice_ratchet.env.*静态：CI 失败；运行期：终止该 tick + P0 事件
E_ENV_AST_DENIED / E_ENV_CODE_SYNTAX黑名单节点/调用/属性；AST 解析失败拒绝该文件；gate() 整批拒绝并保留旧 harness
E_ENV_TIMEOUT工具调用超墙钟该次调用失败 → MOD-04 fallback，不判该局失败
E_ENV_RESOURCE内存/CPU 超限同上；连续 3 次则该 harness 版本标 degraded
E_ENV_ESCAPE受限执行触及蜜罐 sentinelP0 事件 + 立即卸载该 harness 版本，人工确认
E_ENV_AUDIT_IO轨迹缺失/JSONL 损坏/权限不足判 critical（缺证据 ≠ 无泄漏），输出可读原因
E_ENV_HONEYPOT自测命中率 <100%，或注册表含蜜罐字段CI 红；audit leak 恒判 critical

11测试计划

单测路径 tests/unit/sandbox/test_sandbox_{projection,api,guard,audit,honeypot}.py，一律按「给定-当-则」编写：

  • 给定 同一 FullState，当 project_state 调两次，则两次 canonical JSON 与 obs_digest 完全相同（FR-02-1）。
  • 给定 源含未登记字段 hidden_shop_preview，当 mode="strict"，则输出无该字段、dropped_hidden==1、日志文本不含该字段名（FR-02-2）。
  • 给定 seed/后续房间/商店条目/RNG 状态/未来骰面各替换为唯一哨兵值，当 投影后逐字段比对，则任一哨兵出现在 obs 即失败（FR-02-3）。
  • 给定 注册表加字段却不改版本，且源 schema_version="9.9.9"，当 import projection / 执行投影，则分别抛 E_ENV_PROJECTION_VERSION、obs 取注册表版本（FR-02-5/6）。
  • 给定 含 from dice_ratchet.env.engine import Engine 的假 L1 文件 + 已装 import hook，当 check_imports / import dice_ratchet.env.rng，则 ok=False（带行号）、抛 E_ENV_IMPORT_DENIED（FR-02-9/10）。
  • 给定 8 个恶意片段（open("/etc/passwd")、import socket、__import__("os")、eval、exec、getattr(x,"_np_secret_price")、while True、class X），当 analyze_code，则全部被拒且码/行号正确（FR-02-12）。
  • 给定 合法 rank_actions（纯函数，使用 + - * //、比较、and/or/not、推导式、sorted/len/range/max/min），当 gate + worker.call，则通过并返回正确重排（FR-02-12/14，正例必测）。
  • 给定 time.sleep(5) 与申请 1 GB 的两个工具，当 worker.call(timeout_s=0.2)，则分别抛 E_ENV_TIMEOUT（worker 被 kill 并自动重启，下一次调用正常）与 E_ENV_RESOURCE；主进程 RSS 与 rlimit 不变（FR-02-14）。
  • 给定 连续 3 个 reject(final=True)，当 第 3 次调用，则 truncated=True、truncation_reason="policy_failure"；中间插入一次成功决策则计数清零（FR-02-8b）。
  • 给定 legal_actions()，则不含 abandon_run，其余元素与顺序同 MOD-01（FR-02-8c）。
  • 给定 每个 canary/假字段各注入 prompt、memory、log 三类文本，当 honeypot.self_test()，则 12/12 命中、missed==[]（FR-02-23，G4）；给定 无 canary 的正常 prompt，当 honeypot.scan，则 0 命中（无假阳性）；给定 含 train seed 值且该 seed 未出现在 obs 的 synthetic prompt，当 run_audit，则 verdict="critical"、leak_class="seed_leak"、surface="prompt"（FR-02-17/19）。

实现裁决（不改 FR 语义，逐条可复核）

  1. audit leak 退出码为 0/1/2/4：0/1/2 是泄漏结论轴（FR-02-19 与 §11 集成用例），4 是「审计器自身守卫违例」轴（Spec §8.3，与 infra.errors.EXIT_CODE 登记一致）。详见下文两轴表；MOD-09 PRD §6.4 的 0/4 因此只覆盖了后一根轴，已加注。
  2. Observation 是 JSON-native dict：§6 的 project_state(...) -> tuple[dict, ...] 与 obs JSON 示例都是普通映射；§7 的「不可变」由 freeze_observation()（递归 MappingProxyType）与 validate_observation() 按需提供——递归冻结会破坏 deepcopy/序列化，故不设为默认返回类型。
  3. 轨迹行落地归 MOD-06：reject() 不直接写 JSONL（写一行合法轨迹需要 episode_key/generation/harness_version/arm/ts，只有 MOD-06 持有），而是把 illegal=True + reason + reject_stage 放进 StepResult.info 供 MOD-06 单点写行。
  4. legalActionKinds 的 abandon_run 改写落在 projection._REWRITES 表（§6 的 ObsFieldSpec 没有 transform 字段，故不外扩数据类）。
  5. 注册表字段集 = §4.2「保留」表的严格实现：额外排除 chapterName/piles/deck/battleHints/battleKind/outcome（token 预算 + §4.2「删除」的语义；终局结果经 StepResult.info.outcome 提供，不进 prompt）。piles 被排除还使蜜罐向 drawPile 注入虚构骰时不改变 piles.draw 计数。
  6. schema 落 schemas/ 而不是 §6 示例的 dice_ratchet/sandbox/audit/report.schema.json：sandbox/audit.py 已是模块，同名包目录会与模块解析冲突；schemas/ 是 MOD-09 登记的跨模块 schema 根（infra.io.validate 默认搜索路径）。
  7. seed 规则集默认只扫 heldout/test：依 configs/seeds.yaml::exposure_guard.numeric_scan（F45-2 起：「3–6 位数字 token 落 731000-731099 / 947000-947099 即告警」；此前是「4 位落 2000-2099 / 9000-9099」）与 INV-5 的 expose_to；需要更严时 run_audit(seed_splits=("train","heldout","test"))。数值 token 的前导边界含 .：浮点小数部分不再被当 seed（0.731042 不命中 H2），而 "reason": 731042、947042.5、-947042、文本里的 seed 947042 仍命中；数值 token 要求两侧非字母数字。⚠️ 2026-10-14 修订：F45-2 起两张人工死名单（LOG_NON_CONTENT_KEYS / MEMORY_NON_CONTENT_KEYS）已整删——seed 规则现在扫整行字段，仅豁免框架自身的播种计划 LOG_STRUCTURAL_KEYS = {seed, episode_key, spec} ⇒ 扫描面比带名单时更严（不再有字段被跳过）。
  8. import hook 双层：MetaPathFinder（加载期，§4.10 的字面要求）+ builtins.__import__ 包装（缓存命中期）。因为 SandboxEnv 按 FR-02-10 预先 import 了环境层，agent 侧 import dice_ratchet.env.rng 会命中 sys.modules、绕过 finder；只装 finder 会让 FR-02-10 与 §11 的「import dice_ratchet.env.rng → 抛 E_ENV_IMPORT_DENIED」无法成立。
  9. GuardViolation 继承 InfraError（仍是 Exception 子类，符合 §6 签名），从而 CLI 直接拿到 Spec §8.3 的退出码 4，无需第二套错误通道。
  10. _worker.py 是第 6 个（私有）文件：常驻工具子进程的入口必须能被 [sys.executable, "-I", "-S", <file>] 直接执行；5 个公开模块仍只用 stdlib + infra.errors（pyyaml 只在读注入计划时惰性导入）。

audit leak 的四码退出码：两根正交轴（2026-10-03 评审补充）

一次 audit leak 必须同时回答两个互不替代的问题，因此退出码是两根轴而不是一根：

轴问题取值依据
泄漏结论有没有泄漏？0 无 finding / 1 仅 medium / 2 含 criticalFR-02-19、§11 集成用例、§6 verdict 三级
沙箱守卫审计器自己还可信吗？4（machinery_errors 非空，如 E_ENV_HONEYPOT）Spec §8.3「4 沙箱/守卫违例」；infra.errors.EXIT_CODE[E_ENV_HONEYPOT/E_ENV_ESCAPE/E_ENV_IMPORT_DENIED/E_ENV_AST_DENIED] = 4

优先级 4 > 2 > 1 > 0，理由：检测器失效时，报告写 clean 还是 critical 都不能按原义采信——把蜜罐自测失败报成 2 会让 CI 去追一个不存在的泄漏（假警报），而 E_ENV_HONEYPOT 在错误码注册表里本来就是 4。报告同时保留 verdict=critical（FR-02-23：「低于 100% 直接判 critical」）与 machinery_errors，信息不丢，只是分通道表达。

情形轴退出码
干净 run结论0
仅 full_state_field_leak / hidden_field_name_leak（medium）结论1
seed_leak / future_room_leak / shop_content_leak结论2
canary_leak（canary 真的进了 prompt/memory/log）结论2（是发现，不是守卫违例）
蜜罐自测 <100%、注册表含哨兵（E_ENV_HONEYPOT）守卫4
审计路径上触发 import hook / AST 门禁 / 逃逸（E_ENV_*，当前审计本身不执行工具，理论路径）守卫4（由 CLI 通用 except InfraError 给出，无需 run_audit 参与）
E_ENV_AUDIT_IO（轨迹缺失 / JSONL 损坏 / 权限不足）结论2（§10「判 critical」：缺证据 ≠ 无泄漏；码本身在 stdout/报告中显式打印。2026-10-03 评审确认：保留在结论轴，不抬到 4）

run_audit/write_report 不抛异常表达上面任何一条（只读文件、结论入报告）；AuditResult.exit_code 与 AuditResult.exit_reason 是 CLI 的唯一出口。
