MOD-06 loop

闭环的编排器。它不产生策略、不训练模型、不判定好坏，只负责让「打局 → 反思 → 记忆 → 提案 → 评估 → 版本」在三个时间尺度上正确、可复现、可中断、可恢复地跑起来。

L2 进化 ✅ 已落地 2026-10-17 新增 loop baseline 起点守卫

01两个嵌套的循环

“一局”与“一代”是两件事。局是执行单位，代是裁决单位；每 K 局触发一次周期，generation 只在 MOD-07 返回“已裁决”后 +1（接受与拒绝都算）。

02起跑前的三道闸（2026-10-17 起）

为什么守卫放在基线之前。基线本身要花钱（40 局 held-out）。先确认“这个起点是被裁决过的”，再决定是否为它付钱。
现场教训（2026-10-17）：P1 被人工预装成 version 0 的“基线”，从未作为候选过门禁，却成了 P2 的父代。P2 的 accept 建立在 P1 的 held-out 0.05（裸 v0 是 0.175）之上。守卫只保证“没裁决过的东西不会悄悄变成父代”，它不能替代门禁本身。

03loop baseline：把“测一个候选”抽出来

它做什么

对给定的 --harness-dir 跑一次 held-out，落 generations/gen-000/report.json 与臂归档，然后停下。

它不做什么

不训练、不演化、不提交 git、不做裁决。它只产出测量；是否接受仍归 MOD-07 的 C0–C5。

幂等

gen-000/report.json 已存在即直接返回，不重复花钱。幂等键是 run 目录——换 harness 必须换 run-id。

python -m dice_ratchet loop baseline \
  --run-id m3r3 --harness-dir runs/m3r3/harness --basket H1
# 只测 v0+P2 的 40 局 held-out；正式测量 ≈¥33 / ≈1.5 h（--agent heuristic 可免费自检）
为什么需要它。协议纠正后要单独测 v0+P2；原先唯一路径是 loop run，它会把测量和训练/演化绑在一起。把测量抽出来，才能先回答“P2 独立于 P1 还有没有效”这个更便宜的问题。

06当前状态（2026-10-17）

m3r2 的“3 个 cycle”是范围漂移。裁决是 1 个 cycle（先看 P2），脚本的硬编码 seed 上界让它跑了 3 个：262 局、12 h 22 m、¥240.94，比预算多 ≈¥141。范围漂移已修（seed 上界按 CYCLES 推导 + 精确断言）。
协议纠正后：P1 判负 ⇒ v1 = v0；m3r2 的 v1 保留为“含 P1 的 provisional v1”；下一步用 loop baseline 测 v0+P2（40 局 ≈¥33）。在役 harness（version 3）在测完前不动。
